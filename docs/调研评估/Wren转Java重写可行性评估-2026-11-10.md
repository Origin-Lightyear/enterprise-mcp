# Wren 转 Java（并入 customerapp / 独立 Maven 模块）可行性评估

> 评估日期：2026-11-10
> 评估对象：`customer/wren`（Python Adapter + vendored `wrenai 0.14.0` + `wren-core-py 0.8.0`）与 `customer/app`（Spring Boot 4.1.0 / Java 21）
> 方法：逐文件阅读两侧源码，量化调用闭包，核对真实 MDL 与运行状态目录，检索上游是否有 JVM 侧实现
> 相关前置文档：[Wren 单 JAR 部署形态调研](Wren单JAR部署形态调研-2026-09-22.md)、[WrenAI 集成评估](WrenAI集成评估.md)

---

## 一、结论

**可以做，但不应该"把 Wren 翻译成 Java"，而应该"用 Java 重新实现你真正用到的那部分语义层"。这是两件成本相差 5 倍的事。**

三句话版本：

1. **真正的技术债不在 Python，而在 JVM 里没有 `wren-core`（Rust/DataFusion）和 `sqlglot` 的等价物**。Adapter 本身只有 2840 行 Python，重写它只是"去掉外壳"，语义引擎仍在 Rust 核心里。
2. **你现在的真实使用面极窄**：54 个 MDL 模型全部是"一张表 → 一组 camelCase 列"的直映射，**关系 0 条、计算列 0 个、视图 0 个**。也就是说，今天 Wren 为你做的事，90% 是"模型名到物理表的替换 + 只读校验 + 行数限制 + JDBC 执行"——这部分用 Java 写，是 800～1500 行的活，不是移植 25000 行。
3. **建议路径：先用 1～2 周做 `SemanticEngine` 接口解耦（这一步无论走哪条路都必须做，并且立刻解决你说的"强耦合"），再决定是"内嵌 sidecar 收尾"还是"Java 窄语义子集替换"。** 直接全量重写是 30～40 人周且永久脱离上游，不推荐。

**触发条件**（满足任一条才值得走 Java 重写）：

- 客户或交付标准明确不允许在服务器上装 Python / 只接受 JVM 单进程；
- 语义层能力边界可以被产品冻结为"简单模型 + 三个数据库 + 不做关系/指标"；
- 团队无人能长期维护 Python 侧（bus factor = 1）。

**不满足以上条件时的正确答案是**：保持双进程，按《Wren 单 JAR 部署形态调研》把 sidecar 内嵌进 JAR，把"两个交付物"变成"一个交付物、一个启动入口"。那解决的是交付与运维问题，不是语言问题。

## 二、事实基础（评估依据）

### 2.1 当前调用链与代码构成

```text
Agent → customerapp(Java) ──loopback HTTP──→ Wren Adapter(Python) → WrenEngine(同进程)
                                              ├→ wren-core-py（Rust/PyO3，128MB 原生二进制）
                                              ├→ sqlglot（Python，31 方言解析/转写/优化/血缘）
                                              ├→ connector（mysqlclient/psycopg/pyodbc）+ PyArrow
                                              └→ LanceDB（向量记忆，原生扩展）
```

| 组成 | 规模 | 语言 | 是否可平移到 JVM |
|---|---:|---|---|
| Adapter（定制：HTTP 路由、校验、SQL 生成、建模服务） | 2,840 行（非测试；含测试 4,087） | Python | 可，机械工作 |
| upstream `src/wren` 全量 | 25,519 行 | Python | — |
| 其中**实际调用闭包**（context/engine/policy/profile/mdl/model/connector/memory） | 8,683 行 | Python | 大部分可，除 mdl 层 |
| `wren-core-py` | `wren_core.pyd` 128 MB | Rust（DataFusion） | **不可**，无 JVM 绑定 |
| `sqlglot` | 外部依赖 | Python | **不可**，JVM 无成熟等价物 |
| LanceDB | 外部原生扩展 | Rust/C++ | 不可复用索引文件，只能换存储 |

关键事实：`wren.mdl` 只有 50 行，它做的事是**把一切都转交给 `wren_core`**：

```python
# customer/wren/upstream/src/wren/mdl/__init__.py
import wren_core
def get_session_context(...): return wren_core.SessionContext(...)
def get_manifest_extractor(m): return wren_core.ManifestExtractor(m)
def transform_sql(...): return session.transform_sql(sql)
```

而 `engine.py:177 _plan()` 的流程是：`sqlglot` 解析用户 SQL → 抽取相关模型 → `wren-core` 逐模型展开 → `CTERewriter` 把展开结果注回 CTE → `sqlglot` 生成目标方言。**两个"不可平移"的组件被串在同一条链上。**

### 2.2 真实 MDL 使用深度（决定重写成本的隐藏变量）

统计 `customer/wren/project-root/projects/current`：

| 指标 | 实测 | 含义 |
|---|---:|---|
| 模型总数 | 54（shuiqu_db 24 + yiyun_db 30） | 规模不大 |
| 定义关系的模型 | 0（两个 `relationships.yml` 均为 `relationships: []`） | **join 能力未被使用** |
| 含 `expression` 的计算列 | 0 | 表达式求值未被使用 |
| 视图 / `ref_sql` | 0 | 视图未被使用 |
| 列定义形态 | `name + type + raw_type + display_name/description` | 纯表映射 + 中文注释 |

这意味着：**今天 Wren 在你这套部署里，实际只承担"语义表名映射 + 只读拦截 + 行数上限 + JDBC 执行 + 中文 schema 描述"五件事。** 复杂能力（关系、指标、视图、多方言）是"未来可能性"，不是"现在的能力"。

这也意味着成本估算必须分两种口径：**"等价替换现状"和"等价替换 Wren 全集"，二者差 3～5 倍。**

### 2.3 状态与数据

实例目录 `customer/wren/project-root/` 包含：`projects/current/<source>/`（MDL 源文件）、`.wren/profiles.yml`（数据源凭据）、`.wren/memory/`（LanceDB 索引，1.4MB）、`jobs/`（7.5MB 内省快照）、`audit/`（管理审计）。

这些是**升级必须兼容的客户状态**，重写实现必须能读写同一份目录，或提供明确的迁移器。

### 2.4 许可证（一个被忽略但更紧急的问题）

- Wren `core/**` 为 **Apache-2.0**：可以改写、可以闭源分发，需保留 NOTICE 并标注修改。
- **但 `customer/app` 内的管理控制台 UI 改编自 WrenAI GenBI Classic（AGPL-3.0）**，见 `META-INF/NOTICE-WrenAI.md`，AGPL 全文已随 Fat JAR 分发。

**结论：如果你重写 Wren 的动机之一包含"保护 Python 源码不被客户看到"，那么收益远小于既有风险——真正的 AGPL 传染面在已经打进去的 React 控制台，不在 Python。** 建议把许可证梳理列为独立任务，优先级高于 Java 重写。

## 三、要重写的到底是什么（分层拆解）

| # | 层 | 内容 | 现语言 | 重写难度 | 说明 |
|---|---|---|---|---:|---|
| L1 | Adapter 外壳 | 6 个内部 RPC + 约 20 个管理端点、请求校验、service token、requestId | Python | ★☆☆☆☆ | 纯搬运，Spring Controller 天然更合适 |
| L2 | 请求级 SQL 生成 | 拼 prompt、调员工 LLM、解析 `READY/NEEDS_CLARIFICATION`、剥 LIMIT | Python | ★★☆☆☆ | 与 control-plane 的 LLM 调用可复用同一套客户端 |
| L3 | 上下文构建 | MDL YAML → camelCase manifest、`layoutVersion`、schema 描述文本、业务规则 | Python | ★★★☆☆ | 需逐字段对齐，**摘要字节级一致是硬门槛** |
| L4 | 只读策略 | 单语句、禁写、禁 LIMIT、禁 `SELECT *`、结果行上限 | Python(sqlglot) | ★★★☆☆ | 规则简单，但"判定边界"必须与现状一致 |
| L5 | **方言重写** | CTE 注入、列限定、标识符大小写折叠、catalog/schema 限定符剥离、视图 verbatim | Python(sqlglot) | ★★★★★ | **最大风险点**，1176 行里全是方言边角 |
| L6 | **语义展开** | MDL 模型 → 物理 SQL（表达式、类型转换、自定义函数、manifest 抽取） | Rust(wren-core) | ★★★★★ | JVM 无绑定；只能自研 / JNI / 放弃 |
| L7 | 连接器 | 3 个数据库的连接、EXPLAIN、JOIN 式 LIMIT 包裹、Arrow 结果 | Python | ★☆☆☆☆ | **Java 反而更强**（HikariCP + JDBC），这是重写唯一的净收益区 |
| L8 | 向量记忆 | embedding/rerank 调用、LanceDB 索引、原子切换、指纹校验 | Python+LanceDB | ★★★☆☆ | HTTP 部分好搬；LanceDB 必须换存储（pgvector/内存 HNSW），升级需重建索引 |
| L9 | 建模与内省 | 数据源 CRUD、元数据内省 SQL、MDL 编辑/revision/合并、候选-提交、备份恢复 | Python | ★★★☆☆ | 量大但机械，1426 行 admin_service 是主体 |
| L10 | 一致性内核 | MDL digest、候选 token、`expectedMdlDigest`、多源 Engine 生命周期与锁 | Python | ★★★★☆ | 从"进程内锁"变"线程并发"，语义要重新设计而不是照抄 |

**结论：L1～L4、L7～L9 是"工程"，L5～L6 是"研究"。** 任何绕过 L5/L6 的"重写"都只是把 HTTP 换成方法调用，语义引擎仍是 Python/Rust——**这正是你问题里"重写成 Java 到 Customerapp 项目里"最容易被低估的地方。**

## 四、会出现什么问题（逐条给证据与后果）

### P1｜`wren-core` 没有任何 JVM 入口，源码也不在本仓库

- 证据：仓库内只有 `wren_core.pyd`（128MB，PyO3/abi3 扩展）；`pyproject.toml` 依赖 `wren-core-py>=0.8.0`；上游只发布 Python cdylib 与浏览器 WASM（`@wrenai/wren-core-wasm`，约 68MB）。
- 后果：纯 Java 实现必须**自己重新实现 MDL 语义展开**（DataFusion 规模的活），或引入 JNI（仍带原生二进制），或走 WASM（性能与互操作都不成熟）。
- 缓解：见方案 B（JNI 复用 Rust 核心）与方案 C（窄子集自研）。

**上游确实存在过一个 Java 实现**：`Canner/wren-engine`（661 star，Apache-2.0，**已于 2026-05 归档**），其中 `wren-core-legacy` 是 Java 21 + Airlift + ANTLR4 Trino parser 的语义引擎，后被 Rust 版替换。它可以作为**参考实现**，但两点必须清醒：①它已停止维护；②它被替换的原因之一是语义与新版不一致——**不能假设"用 legacy 就能得到今天的 SQL"**。

### P2｜`sqlglot` 在 JVM 没有可用的等价物

- 证据：`CTERewriter` 依赖 `qualify_tables`、`qualify_columns`、`normalize_identifiers`、`MappingSchema`、`lineage`，以及 20+ 方言的生成；`wren_dialect.py` 还注册了自定义方言。
- JVM 候选实况（2026-11 核对）：
  - **JSQLParser**：成熟（5.9k star）、有 `StatementFeatures` 可判只读，但**只做解析与回写，不做跨方言 transpile，不做列限定/血缘**；
  - **Apache Calcite**：有方言适配与校验器，但它是"关系代数 planner"，把任意方言 SQL 读进来再原样吐出去，是它的弱项，不是设计目标；
  - **`gtkcyber/sqlglot_java`**：自称"31 方言 100% 对齐 + optimizer"，但 **GitHub 1 star / 0 fork / 375KB / 2026-02 创建**——不可用于生产，只能当作"这个方向有人试过"的旁证。
- 后果：重写必须**自建"目标方言生成 + 标识符折叠"层**。这里的坑极其具体：
  - Oracle/Snowflake 是 `UPPERCASE` 折叠方言，`CTERewriter` 要用 `identify=True` 全引号输出，否则聚合别名大小写变化会直接改结果列名；
  - 非引号标识符在不同方言下折叠规则不同，模型 CTE 暴露列时必须与用户书写时的引号形态一致，否则 CTE 绑定失败（`_alias_projection_to_user_quoting`）；
  - `EVIAN_CDSP.dbo.e_order` 这类三段限定符要"识别并剥离 MDL 已声明的 catalog/schema"；
  - 还有只允许在"物理列名大小写敏感方言"上存在的列名冲突检测。
- 缓解：把 L5 限定为"只支持 MSSQL/MySQL/Postgres 三种折叠策略"，并把这些行为写成 fixture 对拍。

### P3｜MDL Digest 必须**字节级**一致，否则升级瞬间全量计划失效（最隐蔽、后果最重）

- 证据：`server.py:132 mdl_digest()` 对 manifest 做 `json.dumps(..., sort_keys=True, separators=(",",":"), ensure_ascii=False)` 后 sha256；聚合摘要是"每源摘要字符串"再排序序列化后二次 sha256。control-plane 用该摘要绑定 Catalog 与计划（见 `CONTEXT.md`：MDL Update 需 Control Plane 确认同摘要，否则 Current MDL 不变）。
- 后果：只要 Java 侧的 JSON 序列化有一处不同——键序、空格、浮点格式、非 ASCII 是否转义、`null` 与缺省、`layoutVersion` 位置——摘要就全变：**Catalog 不匹配 → 全部 Runtime 进入 NOT_READY，所有在飞计划作废，升级当场变成事故**。
- 缓解：必须做"同一 `projects/current` 目录，Python 与 Java 生成的 manifest 逐字节 diff + digest 相等"的专项测试，作为**上线门禁**，而不是普通单测。

### P4｜结果类型契约会漂移（用户可见）

- 证据：Python 走 Arrow → `table.to_pylist()` → `json.dumps(default=str)`。因此 `DECIMAL` 落成字符串、`datetime` 落成 ISO、`BIT` 落成 bool。真实模型里 DECIMAL 列很多（`receivableTotal`、`freight`、`discountMoney`…）。
- Java 用 JDBC 会得到 `BigDecimal` / `Timestamp` / `Boolean`，Jackson 默认把 `BigDecimal` 输出成数字、`Timestamp` 输出成时间戳数字或按 JVM 时区序列化。
- 后果：Agent 与前端看到的类型/精度/时区变化；Excel 导出格式变化；`DATE` 类型在跨时区时**日期整体偏移一天**（MSSQL `datetime` 是 naive 的，JDBC 会按 JVM 默认时区解释）。
- 缓解：建立"源类型 → JSON 表示"的显式映射表，强制 `tenant-zone`（配置里已有 `saas.tenant-zone: Asia/Shanghai`），并写契约测试逐类型锁定。

### P5｜并发模型从"单线程串行"变"多线程并发"，一致性要重新设计

- 证据：`WrenRuntime` 用一把 `RLock` 把"摘要校验 → 查询 → 结果回填"整体串行化，`commit_project` 用 `os.replace` 做原子替换并在锁内换 Engine；连接器每个源只有**一个长连接**。
- 后果：Java 天然并发后，若照抄成"无锁"，会出现"查询按旧 MDL 解释、提交按新 MDL 校验"的错配；若照抄成"一把大锁"，则并发收益为 0，且长查询会阻塞建模提交。
- 缓解：不可变快照 + 版本号 + CAS 提交 + 旧句柄引用计数（请求入口 pin 快照，提交只换引用，最后一个引用释放时关闭连接）；每源连接池上限 2～4，避免把客户库打挂。

### P6｜向量记忆的索引格式不可复用

- 证据：`retrieval.py` 用 LanceDB（`lancedb==0.38.0`）存 `schema_memory`/`query_memory`，目录按 `sourceKey / mdlDigest / embeddingModelHash` 分层并带 `metadata.json` 指纹；升级到 Java 后这份 `.lance` 数据无法读取。
- 后果：升级后首次查询触发全量重建索引（对 54 模型 × 每列一条记录，一次性打 embedding 接口，耗时与费用都不可忽略）；若 embedding 维度变化，还会直接失败。
- 缓解：换 pgvector / 内存 HNSW，保留"指纹 + 维度 + 模型名"三元校验与原子切换语义；升级脚本负责预热重建，禁止在首个用户请求里同步重建。

### P7｜管理控制台的错误语义与乐观锁容易在重写中丢失

- 证据：`WrenAdminController` 是薄代理，前端 `api.ts` 全部走 `/internal/wren/admin/*`；Adapter 用状态码表达业务语义：401 认证失败、404 KeyError、409 `PROFILE_IN_USE` / `MODELING_CHANGED` / `CURRENT_MDL_CHANGED` / `INTROSPECTION_IN_PROGRESS`，另有 `revision` 乐观锁与 `candidateToken` 两步提交。
- 后果：合并后若"顺手简化"，UI 会静默丢冲突检测，出现"两人同时改模型，后者覆盖前者"或"MDL 被改但 Catalog 未确认"。
- 缓解：这些语义必须在 Java 内显式重建，并把现有 62 个 Python 测试（`test_admin_service.py` 27 个）转成 Java 契约测试。

### P8｜备份/恢复要跨版本兼容

- 证据：`create_backup()` / `restore_backup()` 打 zip 并校验；客户运维可能拿着旧版本备份恢复到新版本。
- 后果：新实现不认旧 zip，或恢复后 MDL/profiles 结构与新代码不匹配。
- 缓解：备份格式显式版本化，提供"v1 读取 + v2 写入"的向上迁移。

### P9｜安全边界会改变（文档与审计口径要跟着改）

- 证据：`WrenDatabaseTool` 的注释明确"**不在 customerapp 内维护 JDBC 连接**"；凭据在 `profiles.yml`，由 sidecar 独占；sidecar 用 loopback + 每次启动的 service token 做隔离。
- 后果：合并后 customerapp 进程内存中直接持有客户数据库凭据与连接。同一台机器、同一信任域，**安全性并未实质性下降**，但"凭据只在独立进程内"的架构承诺失效，密钥注入、审计、崩溃转储（heap dump 会带出密码）都要重新评估。
- 收益：service token、端口冲突、loopback 认证、双进程孤儿这些问题全部消失。
- 缓解：改为从环境变量/Secret Provider 注入并用 `char[]` 持有；关闭生产 heap dump；审计补记"同进程数据库访问"。

### P10｜测试与上游同步成本

- 证据：Adapter 62 个测试 + 上游 `tests/` 套件；上游版本在持续演进（CHANGELOG 密集，涉及 SQL 正确性与安全修复）。
- 后果：fork 出 Java 实现即等于**永久分叉**，上游每次修 SQL 生成、方言兼容、MDL 演进的补丁都要人工判断"是否需要在我们这里重做一遍"。这是长期成本，不是一次性成本。

### P11｜性能收益很可能被高估

- 事实：单次查询耗时构成大致是 LLM 生成（**1～3 秒**）+ 数据库执行（10ms～数秒）+ 结果序列化/HTTP（**约 5～30ms @1000 行**）。
- 结论：**单进程主要省的是启动时间、内存与运维复杂度，不是查询延迟。** 若决策理由写成"提升性能"，应先用 metrics 证明 HTTP 跳转是瓶颈——大概率不是。反过来说，Java 的净收益在 L7（连接池、并发）与 L2（复用已有 LLM 客户端、避免重复实现鉴权与超时）。

### P12｜能力覆盖会缩水，销售口径要同步

- 今天文档宣称支持 20+ 数据源；Java 首版若只做 MSSQL/MySQL/Postgres，等价于产品能力收缩。`系统说明.md` 第 7 节、Catalog、Control Plane 的能力声明都要跟着改，否则形成"虚假宣传"。

## 五、方案对比

| 方案 | 单进程/JVM | 语义一致性 | 工作量（人周） | 长期维护 | 主要风险 | 适用条件 |
|---|---|---:|---:|---|---|---|
| **A. 保持双进程，做 SPI 解耦 + 内嵌 sidecar** | 否（1 交付物 2 进程） | 100%（就是同一个） | 2～4 | 低（跟上游走） | 无架构风险；仅交付形态 | 目标是交付/运维简化 |
| **B. SPI + JNI 包一层 Rust `wren-core`** | 是（仍带 .dll/.so） | 高（引擎同源） | 10～16 | 中（要跟 Rust crate API） | 需自建 Rust cdylib + JNI/FFI、跨平台构建、崩溃会拖垮 JVM；L5 仍要 Java 重做 | 必须单进程、且接受原生库 |
| **C. 纯 Java 重写「窄子集」**（3 库 + 简单模型 + 无关系） | 是 | 中（现状等价，未来受限） | 14～20（MVP） | **高**（自己养方言层） | L5 方言边角、P3 摘要一致性、P4 类型漂移 | 客户禁 Python + 能力可冻结 |
| **D. 纯 Java 重写「全集」**（C + 关系/计算列/视图/多方言） | 是 | 低～中 | 30～40+ | 极高（等于自研语义层） | 全部 P1～P12 | 有专职团队且愿长期投入 |
| **E. 用 Apache Calcite 重建语义层** | 是 | 低（语义需重新定义） | 20～30 | 中高（社区大但方言生成弱） | 同上 + Calcite 方言输出调优 | 想借成熟 planner 而非自己写 AST |
| **F. Java 直译 + Python 兜底（双实现）** | 半 | 不可控 | 18～25 | **最高（双份漂移）** | 两套语义逐渐不一致且难定位 | 不推荐 |

**推荐排序：A（若目标是交付）→ C（若目标是单进程）→ B（若 C 卡在语义）→ D 基本不做 → F 不做。**

一条补充判断：**如果产品路线图里"关系/指标/多方言"在 12 个月内不会落地，方案 C 的"窄子集"就是等价替换，成本可控；一旦要落地，C 会立刻退化成 D。** 所以这个决策本质上是在问产品：语义层要不要继续长大。

## 六、推荐实施路径（无论选 B/C，前两步都一样）

### 阶段 0：解耦（1～2 周，必做，零风险，立刻见效）

在 `customer/runtime` 定义 SPI，把"调用 Wren"变成"调用语义引擎接口"：

```text
customer/runtime ... com.kevin.mcp.semantic
  SemanticEngine                 # 唯一的引擎契约
  MdlSnapshot(sourceKey, digest, manifest, version)   # 不可变快照
  SemanticQuery / SemanticResult / SemanticError
  SemanticEngineProvider         # 按配置选择实现
customer/app ... com.customer.mcp.wren
  SidecarSemanticEngine          # 现有 WrenSidecarClient 包一层（今天就能用）
  （未来）NativeSemanticEngine   # 纯 Java 实现
customer/app/application.yml
  enterprise.semantic.engine=sidecar|native
```

这一步的收益**与是否重写无关**：

- `WrenDatabaseTool` / `WrenAdminController` 不再直连 `WrenSidecarClient`，耦合从"HTTP 细节"降到"7 个方法"；
- 健康聚合、超时、错误码映射收敛到一处；
- 为"影子对比"（见阶段 2）留出插槽。

### 阶段 1：冻结合同 + 建"金标准"数据集（1～2 周）

用**现有 Python 实现当 oracle**，产出可 diff 的 fixture：

```text
testdata/semantic/<case>/
  mdl/                      # 复制真实 projects/current/<source>
  input.json                # sql / question / limit / expectedMdlDigest
  expected.plan.sql         # dry_plan 输出（逐字符）
  expected.result.json      # columns/rows/truncated（逐类型）
  expected.error.json       # 错误码 + HTTP status
  expected.digest.txt       # manifest 字节 + sha256
```

覆盖：3 个数据源方言 × {简单聚合、多表 JOIN（未来）、中文列名、DECIMAL、DATETIME、NULL、重复列名、超限截断、只读拦截、禁止 `SELECT *`、禁止 LIMIT}。

**这套 fixture 是整个项目的真正资产**：它同时是 Java 实现的需求文档、回归门禁，也是回滚依据。

### 阶段 2：Java 实现（按 L 层推进，每层都有门禁）

| 步 | 内容 | 门禁 |
|---|---|---|
| 2.1 | MDL 解析 + camelCase manifest + **digest 字节级对齐** | P3 专项：与 Python 逐字节 diff，全绿才继续 |
| 2.2 | 只读校验（JSQLParser `StatementFeatures` 或自研 AST 白名单） | 拦截用例 100% 一致 |
| 2.3 | JDBC 执行 + HikariCP + 类型映射 + `limit+1` 截断语义 | 结果 JSON 逐字段一致（含 DECIMAL/时间） |
| 2.4 | CTE 注入 + 三方言标识符折叠 | `expected.plan.sql` 可接受差异清单（见下） |
| 2.5 | 建模/内省/候选-提交/备份恢复迁移 | 62 个 Python 测试语义等价 |
| 2.6 | 向量记忆替换 | 索引重建 + 维度校验 + 降级路径 |
| 2.7 | 影子模式：Java 算 plan 只打日志，仍返回 Python 结果 | 连续 N 天差异率 = 0 才切流 |

关于 2.4 的"可接受差异"：**物理 SQL 的文本不要求逐字符相同**（别名、括号、空白可不同），但必须满足：①语义等价（在真实库上返回同结果集）；②输出列名与顺序一致（下游按名取列）。建议 fixture 同时存"文本"和"结果集"两种断言，以结果集为主。

### 阶段 3：切流与回滚

- 配置开关 `enterprise.semantic.engine`，可按 sourceKey 灰度；
- 任一阶段失败 → 切回 `sidecar`，state 目录不动（阶段 2 全程只读 Python 的目录，不写入）；
- 只有"全部 sourceKey 在 native 下连续稳定 + 一次真实升级"通过，才允许移除 Python 侧打包。

### 并发与一致性设计（Java 专用，不能照抄 Python）

```text
MdlRegistry
  ConcurrentHashMap<String, SourceState>       // SourceState 不可变
  SourceState { long version; String digest; Map manifest; EngineHandle handle; }
query():
  s = registry.get(sourceKey)                  // pin
  if (req.expectedMdlDigest != null && !req.expectedMdlDigest.equals(globalDigest())) fail fast
  执行 → 用 s.handle 的只读连接
commit():
  registry.compute(sourceKey, (k, cur) -> {     // CAS on version
     if (cur.version != expectedVersion) throw CURRENT_MDL_CHANGED;
     return new SourceState(version+1, newDigest, newManifest, newHandle);
  })
  old.handle.retireWhenUnreferenced()          // 引用计数，最后一个请求结束后 close
```

要点：**摘要校验仍然必须做**。合并成同进程后它的作用从"防止跨进程读到新 MDL"变成"计划绑定校验"，是 control-plane 契约的一部分，不能因为"同进程了不需要"而删掉——这正是最容易犯的错。

## 八、明确不做什么

1. 不逐行翻译 `context.py` / `cte_rewriter.py` / `policy.py`——照抄会把 sqlglot 的隐含假设带进 Java，却丢掉它的方言库。
2. 不在第一版实现"20+ 数据源"。先 3 个，其余明确标注不支持并在 Catalog 里体现。
3. 不因为"同进程了"就删掉 `expectedMdlDigest`、`candidateToken`、`revision`、`409` 冲突语义——它们是 UI 与 control-plane 的契约。
4. 不在 Java 侧重新设计 MDL 文件格式。**目录与 YAML 结构必须与现在完全一致**，否则客户的建模资产要迁移，升级风险翻倍。
5. 不用 `gtkcyber/sqlglot_java` 这类 1 star 的第三方移植做生产依赖；可以读它的实现思路，不作为依赖。
6. 不把"重写"和"AGPL 控制台治理"混在一个项目里——后者优先级更高，且独立。

## 九、需要你决策的三个问题

1. **真实约束是什么？** 是"客户服务器不能装 Python / 只要 JVM 单进程"（→ 方案 C），还是"两个进程运维太麻烦、升级不原子"（→ 方案 A 就够），还是"担心 Python 源码被看到"（→ 先处理 AGPL 控制台，重写收益有限）？
2. **语义层要不要长大？** 12 个月内是否要支持"跨表关系 / 计算字段 / 国产数据库 / 更多方言"？要 → 方案 C 会退化成 D，建议选 A 或 B；不要 → C 是等价替换，值得做。
3. **谁维护？** 重写后 Rust/方言层由谁负责长期追上游？如果没有明确的人，方案 D 的隐性成本会在 12 个月后集中爆发。

## 十、一句话总结

> 你现在的"两个服务强耦合"，本质不是 Python 与 Java 的语言问题，而是 **customerapp 把语义模型的所有权交给了另一个进程，并且每次查询都要跨进程再取一次上下文**。
> 先用 `SemanticEngine` 接口把这条边界说清楚（1～2 周），"强耦合"就解决了一半；
> 剩下那一半要不要用重写来解决，取决于你能接受"语义层停止生长"还是"养一支自己的 SQL 方言团队"。
