# WrenAI 澄清与追问机制调研

核查日期：2026-09-21  
核查范围：WrenAI 当前 OSS `main`（commit [`871118e`](https://github.com/Canner/WrenAI/tree/871118e94f1525c401d867074c05e7e8eefca1cc)）、Classic `v1-final`（commit [`e42b8d0`](https://github.com/Canner/WrenAI/tree/e42b8d057c611016d781c7bbe74ba4e5aeb9712d)）以及本仓库 Customerapp -> Wren Adapter 现行实现。官方结论只引用 Canner/WrenAI 官方源码和官方文档。

## 结论

1. **当前 OSS Wren MCP Server 本身没有 `NEEDS_CLARIFICATION`、`ask_user` 或 MCP elicitation 返回协议。**它暴露的是查询、Schema、知识、资源和 workflow prompt；是否需要追问以及怎样向用户提问，由调用它的宿主 Agent 决定。
2. **当前官方 Agent/Skill 路线支持追问，但能力在宿主 Agent，不在 Wren Engine 或 MCP Server 内。**官方架构明确把 Ambiguity detection 放在 “Skill orchestration by the agent”，并写明 Agent 可在需要时 “ask a clarification”。Skill 文件中的 “Ask the user” 也是给宿主 Agent 的提示指令，不是 Wren 服务端向客户端发出的事件。
3. **Classic WrenAI 有一套较弱的“澄清式交互”。**它会结合 Schema 和历史问题做意图分类，把 vague query 分类为 `MISLEADING_QUERY`，流式生成解释和更合适的问题建议；用户可以在同一 thread 中继续问。但它没有为“两个语义相似字段”定义稳定的候选项、置信度、`clarificationId` 或待恢复状态，因此不能等同于结构化字段消歧协议。
4. **Customerapp 调 Wren 并不会从架构上阻断追问。**Classic 也是 UI/服务主动 POST、轮询结果并连接 SSE，不是 Wren 主动建立一条到用户的反向连接。本项目目前已有规划前的弱澄清：Control Plane 遇到实质歧义时可以返回 `error`，外层 Agent 据此让用户重述。真正的缺口在本地 `/internal/query`：它仍是一次性 `question -> SQL -> result/error`，请求不带对话历史，LLM 被要求只能返回含 `sql` 的 JSON，响应也没有字段候选或“需要澄清”分支。因此现在不能自动继承 Wren 的字段级澄清体验，但可以扩展 Customerapp/Runtime/Agent 的回合协议实现。

## 两代 Wren 不应混用

| 对象 | 自然语言编排位置 | 是否存在服务端结构化澄清协议 |
| --- | --- | --- |
| 当前 OSS `main` 的 Wren Engine/MCP | 外部 Agent + Wren Skills | 否 |
| Classic WrenAI `v1-final` 的 Ask Pipeline/UI | `wren-ai-service` 做意图分类，Wren UI 维护 thread 并展示流式回答 | 有模糊问题引导和 follow-up，但没有字段候选确认协议 |
| 本项目 Customerapp + 定制 Adapter | Adapter 内一次 LLM 生成 SQL，Customerapp 同步转发 | 否 |

## 当前 OSS Wren MCP：澄清属于宿主 Agent

当前官方架构把 Schema linking、Ambiguity detection、Retry/repair 拆成可编排原语。其中 Ambiguity detection 的归属明确是 **Skill orchestration by the agent**；官方流程也写成 Agent 获取上下文、生成 SQL、调用 Wren dry-plan/validate/execute，然后由 **Agent** 修复或追问：

- [Architecture：Ambiguity detection 的归属和 Agent 追问](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/docs/core/reference/architecture.md#L10-L23)
- [Architecture：Agent-assisted query 流程](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/docs/core/reference/architecture.md#L196-L207)
- [What is context：何时应在写 SQL 前澄清](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/docs/core/concepts/what_is_context.md#L11-L22)

官方 MCP 文档列出的能力是：

- 查询：`run_sql`、`dry_run`、`dry_plan`、`query_cube`；
- Schema：`get_mdl`、`list_models`、`describe_model` 等；
- 知识：`get_instructions`、`recall_queries`、`get_context` 等；
- 资源和 `wren_workflow` prompt。

完整工具清单见 [Serve an MCP server - What the client gets](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/docs/core/guides/mcp.md#L71-L88)，注册入口见 [`build_server`](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/mcp_server.py#L687-L699)。源码中没有 `NEEDS_CLARIFICATION`、`ask_user`、`elicitation` 或 `elicit()` 分支；`run_sql` 和 `dry_run` 只返回结果/成功，失败时抛出错误，见 [`_register_query_tools`](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/mcp_server.py#L115-L210)。

`wren_workflow` 只是返回一段供客户端 Agent 执行的 SOP 文本，不创建会话、暂停请求或向用户发送问题，见 [`_workflow_text`](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/mcp_server.py#L637-L684)。官方 Skills 中的提问规则同样是提示宿主 Agent，例如建模流程要求在无法独立决定 canonical table 或 ambiguous foreign key 时问一个聚焦问题：[Model your business](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/docs/core/guides/model.md#L16-L26)。

所以，对当前 OSS Wren MCP 的准确表述是：**Wren 提供让 Agent 判断歧义所需的上下文和校验工具；真正发问的是 MCP 客户端中的 Agent。**

## Classic Ask API：有引导和续问，但不是结构化字段确认

### 1. 请求、异步状态和结果接口

Classic `POST /v1/asks` 接收 `query`、`mdl_hash` 和 `histories[{question, sql}]`，立即返回 `query_id`；客户端随后读取结果或 SSE：

- 请求/结果模型：[`AskRequest`、`AskResultResponse`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L16-L94)
- API：`POST /asks`、`GET /asks/{query_id}/result`、`GET /asks/{query_id}/streaming-result`，见 [Ask router](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/routers/ask.py#L25-L79)
- SSE 数据契约是 `data: {"message":"..."}`，见 [`SSEEvent`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/__init__.py#L44-L54)。

这仍然是**调用方拉取/订阅**：Wren 服务不会脱离现有请求链路主动找到用户。

### 2. 模糊问题的识别和引导回答

Intent Classification 会把当前问题、历史问题、Schema、指令合并判断。其 prompt 明确要求 vague query 分类为 `MISLEADING_QUERY`，缺少参数的 incomplete query 分类为 `GENERAL`，并把 follow-up 改写成独立问题，见 [`intent_classification_system_prompt`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/generation/intent_classification.py#L25-L78)。

当结果为 `MISLEADING_QUERY` 时，Ask Service 启动 `misleading_assistance` 流式任务并结束 SQL 生成分支，见 [`AskService.ask`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L236-L280)。该 assistance prompt 的目标是解释数据并“suggest few better questions to ask”，同时禁止输出 SQL，见 [`misleading_assistance_system_prompt`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/generation/misleading_assistance.py#L20-L51)。流式路由会按 `query_id` 从对应 pipeline 输出 SSE，见 [`get_ask_streaming_result`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L667-L693)。

这里的任务会被立即写成 `status="finished", type="GENERAL"` 后返回，并不存在 `awaiting_user` 或 suspended 状态。`AskResultResponse` 的状态枚举也只有 `understanding/searching/planning/generating/correcting/finished/failed/stopped`，结果类型只有 `GENERAL/TEXT_TO_SQL`，见 [`AskResultResponse`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L64-L94)。

UI 通过 EventSource 累加 `message` 并在 `done` 时关闭，见 [`useAskingStreamTask`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/hooks/useAskingStreamTask.tsx#L21-L43)；服务端代理补充 `done` 事件，见 [streaming API route](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/pages/api/ask_task/streaming.ts#L15-L32)。UI 代码也定义了 `Clarification needed` 状态，见 [`Prompt/Result.tsx`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/components/pages/home/prompt/Result.tsx#L249-L291)。

### 3. 如何继续会话

Wren UI 的 `AskingTaskInput` 带可选 `threadId`，见 [GraphQL schema](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/apollo/server/schema.ts#L604-L626)。创建 follow-up 时，UI 服务按 thread 读取历史响应并转换成 `histories[{question, sql}]` 后传给 `/v1/asks`：

- [按 thread 读取 history 并调用 Ask](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/apollo/server/services/askingService.ts#L584-L611)
- [转换 history 请求](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/apollo/server/adaptors/wrenAIAdaptor.ts#L230-L243)
- [history 只包含 `question` 和 `sql`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/apollo/server/adaptors/wrenAIAdaptor.ts#L926-L935)

这里有一个重要边界：UI 只保留有 SQL 的 thread response 作为 Ask history，见 [`getAskingHistory`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/apollo/server/services/askingService.ts#L1158-L1179)；AI Service 默认最多取 5 条，见 [`AskService.ask`](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L133-L154)。因此它不是保存“系统问了哪个候选字段、用户选择了哪个选项”的完整暂停/恢复状态机。

### 4. “相似字段需要确认”能做到什么程度

Classic pipeline 的 LLM 可能根据 Schema 将模糊输入判为 `MISLEADING_QUERY` 并建议用户具体化，也可能在下一轮根据 history 理解 follow-up。但是官方源码未定义：

- 相似字段候选列表及稳定字段 ID；
- 置信度阈值；
- `clarificationId` / pending turn；
- 单选、多选、自由文本等回答 Schema；
- 用户回答后从原执行节点恢复的协议。

所以它是**启发式的自然语言引导**，不是可审计、可恢复的字段消歧工作流。SQL 生成失败时的 `NO_RELEVANT_SQL` 也只是失败结果，虽然 UI 短标题显示 `Clarification needed`，并不携带可恢复的确认对象，见 [Ask failure branch](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L583-L618) 和 [UI error mapping](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ui/src/apollo/server/utils/error.ts#L133-L155)。

### 5. 官方未合并的澄清草稿不能算正式能力

官方 Draft PR [#1874 improve ask experience](https://github.com/Canner/WrenAI/pull/1874) 曾增加 `USER_CLARIFICATION` intent 和 `user_clarification_assistance`。但该 PR 仍处于 Draft、未合并；其实现同样在生成 Markdown 引导文本后把请求置为 `status="finished", type="GENERAL"`，见草稿 commit `9e789da` 的 [`AskService`](https://github.com/Canner/WrenAI/blob/9e789da7fcb5be1dbd997f5b90446f87a104ba68/wren-ai-service/src/web/v1/services/ask.py#L387-L410)。它没有引入候选字段、回答 Schema 或 resume token，不能作为正式版已有暂停/恢复澄清机制的证据。

## 本项目当前能做到什么、缺少什么

本项目不是在运行 Classic Ask Pipeline，也没有直接使用当前 OSS MCP Server 的 Agent 编排；当前链路是：

```text
Agent / Runtime
  -> Customerapp WrenDatabaseTool.query(sourceKey, question, outputMode)
  -> WrenSidecarClient POST /internal/query
  -> 定制 Adapter 检索 Schema/规则
  -> 一次 LLM 调用，强制只返回 {"sql": "..."}
  -> 执行并同步返回结果，或返回结构化错误
```

代码证据：

- [`WrenDatabaseTool`](../../customer/app/src/main/java/com/customer/mcp/capability/WrenDatabaseTool.java) 只构造 `sourceKey`、`question`、`outputMode`、`expectedMdlDigest` 和 LLM 配置，没有 conversation/history/turn。
- [`WrenSidecarClient`](../../customer/app/src/main/java/com/customer/mcp/wren/WrenSidecarClient.java) 把请求同步 POST 到 `/internal/query` 并直接返回 Map。
- [`server.py`](../../customer/wren/adapter/server.py) 的生成 prompt 要求 “Return only one JSON object with a sql field”，消息只有 system + 当前 user question；路由随后立即执行 SQL。

需要区分歧义出现的阶段：

- **云端生成执行计划前**：已有弱澄清能力。[`PlanningPrompt`](../../cloud/control-plane/src/main/java/com/kevin/mcp/cloud/planning/prompt/PlanningPrompt.java) 第 13 条要求数据库术语、时间范围或目标对象存在实质歧义时返回 `error`；[`CommonInternalTool`](../../customer/runtime/src/main/java/com/kevin/mcp/tools/CommonInternalTool.java) 会把该失败计划作为 Tool 结果返回。因此外层 Agent 可以向用户追问，再用完整的新问题重新规划。
- **Adapter 检索到相似模型/字段后**：当前没有合法的“向上返回澄清候选”出口。Adapter LLM 只能生成 SQL，或生成/校验失败；后者最终通常变成通用查询失败，而不是用户可回答的问题。

这说明本项目已有“停止猜测”的基础规则，但还没有字段级、结构化、可审计的澄清工作流。缺口来自**本项目契约**，不是 “Customerapp 位于中间层” 导致的技术不可能。

另外，当前项目使用 Spring AI `2.0.0`；本机依赖中的 `McpSyncRequestContext` 已提供 `elicitEnabled()` 和 `elicit(...)`。项目所用 Agent 已由产品侧确认支持 MCP Elicitation，因此 Customerapp 可以在一次 Tool 调用内请求用户输入。当前代码已按该能力实现；但本次开发环境尚未完成真实 Agent 到 Customerapp 的 Elicitation 端到端验证，生产验收仍需覆盖能力协商、用户接受、取消和超时。

## 经 Customerapp 保留追问能力所需协议

推荐让 Customerapp/Adapter 返回**有判别字段的回合结果**，由 Runtime/Agent 负责真正向用户显示并在下一轮恢复。不要把澄清当 HTTP 500，也不要让 Wren sidecar尝试主动连接用户。

最小响应契约：

```json
{
  "outcome": "NEEDS_CLARIFICATION",
  "conversationId": "...",
  "turnId": "...",
  "clarification": {
    "id": "...",
    "question": "这里的销售日期是指下单时间还是支付时间？",
    "reason": "MULTIPLE_SEMANTIC_FIELDS",
    "options": [
      {"id": "Order.createdAt", "label": "下单时间"},
      {"id": "Order.paidAt", "label": "支付时间"}
    ],
    "allowFreeText": true
  },
  "binding": {
    "sourceKey": "erp",
    "mdlDigest": "..."
  }
}
```

下一轮至少要提交 `conversationId`、`clarification.id`、用户答案，以及原请求绑定的 `sourceKey`/`mdlDigest`。服务端还需要保存或可靠重建：

1. 原始问题、已确认约束、候选字段的稳定语义 ID；
2. tenant/employee/request 身份和权限上下文；
3. 使用的 Current MDL digest，避免确认期间 Release 改变后把答案套到另一版模型；
4. 过期时间、幂等 turn ID、最大澄清轮数和取消状态；
5. 澄清问题、候选项、用户回答、最终 SQL/结果的审计链。

传输可以是普通请求/响应，也可以由 Customerapp 代理 SSE；SSE 只影响逐字展示，不解决会话状态。Customerapp 在 5 分钟有界超时内通过 `McpSyncRequestContext.elicit(...)` 收集本轮答案；若能力协商失败或超时，则终止本次查询，不继续猜测，也不无限挂起第一次计划。

## 建议归属

结合当前官方 Wren 的设计，推荐职责如下：

- **Wren/Adapter**：检索语义候选、识别本地 MDL 中的歧义、返回结构化候选和绑定信息；不直接面向用户。
- **Customerapp**：守住本地 Schema/MDL 和员工权限边界，签发/校验 clarification token，持有短期 pending state。
- **Runtime/Agent**：把 `NEEDS_CLARIFICATION` 转成用户可见问题，收集回答，携带会话身份继续调用。
- **最终 UI**：展示候选选项和自由文本入口；明确“尚未执行查询”，避免把澄清文字当查询结果。

如果仅需要接近 Classic 的体验，可以先返回一段自然语言建议并让用户重问；如果目标是生产可审计的“相似字段确认”，则应实现上述结构化契约，不能只复制 Classic `MISLEADING_QUERY` prompt。

## 最终判断

- 问“原 Wren 有没有拿不准再问用户”：**Classic 有启发式的模糊意图引导和续问；当前 OSS Wren 也支持这种工作方式，但由宿主 Agent/Skill 编排。两者都没有开箱即用的结构化字段确认协议。**
- 问“定制 Wren 能否向用户发起提问”：**能，但 Wren 应先返回结构化澄清结果给 Customerapp，再由 Customerapp 通过 MCP Elicitation 在当前 Tool 调用内发问。Wren 本身不跨层主动推送。**
- 问“Customerapp 调 Wren 是否就不能实现”：**不是。代理层不会阻断，当前一次性接口契约才是限制；补齐结果类型、会话状态、暂停/恢复和 UI 展示后即可实现。**
