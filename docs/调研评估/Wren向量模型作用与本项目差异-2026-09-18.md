# Wren 向量模型作用与本项目差异

> 调研日期：2026-09-18  
> 结论范围：Wren GenBI Classic `v1-final`（提交 `e42b8d057c611016d781c7bbe74ba4e5aeb9712d`）、当前 Wren OSS（提交 `871118e94f1525c401d867074c05e7e8eefca1cc`）以及本仓库当前实现。  
> 资料范围：仅使用 Wren 官方 GitHub 仓库的固定提交源码；本仓库代码只用于核对当前定制链路。

## 一句话结论

Wren 官方配置的向量模型不是用来连接数据库或执行 SQL，而是把用户问题与 Schema、历史问题、已确认的 NL-SQL 样例和业务指令做语义相似度检索，再把召回内容交给 LLM 生成 SQL。SQL 生成后，真正的规划、校验和数据库执行不再调用向量模型。

本项目改造前没有配置向量模型，是因为定制 Adapter 尚未走这套检索链路：它把当前数据源的完整 MDL `manifest` 直接放入员工 LLM 的 prompt，取得 SQL 后交给 `WrenEngine` 执行。这种实现只适合小规模 Schema，不表示向量模型已经被 Wren Engine 内部替代。现在代码已按官方混合策略补入 Schema/Query Memory：小 Schema 仍发送完整描述，大 Schema 先用员工向量模型召回相关上下文，不再每次发送完整 MDL。

## 必须先区分两代官方 Wren

### 1. Wren GenBI Classic

用户在官方旧版部署配置中看到的 `embedder`、Qdrant 和 `embedding_model_dim` 属于 Wren GenBI Classic。固定版本的示例配置声明 `litellm_embedder`，默认模型为 `text-embedding-3-large`，Qdrant 的向量维度为 `3072`，并把 Schema、历史问题、SQL pairs 和 instructions 的索引/检索 pipeline 接到 embedder 与 Qdrant：[官方配置](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/docker/config.example.yaml#L47-L93)、[SQL pairs 与 instructions 配置](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/docker/config.example.yaml#L125-L156)。

因此对 Classic 的 AI Service 来说，embedding 配置是其 RAG pipeline 的运行依赖。模型与 Qdrant 中既有向量的维度必须一致；更换为不同维度的模型需要重建对应索引，不能只改模型名。

### 2. 当前 Wren OSS CLI/SDK

当前官方 OSS 已不是 Classic 的六容器 GenBI 架构。其基础安装不强制安装向量依赖：`memory` 是可选 extra，才引入 LanceDB 与 `sentence-transformers`；另有基于 ONNX 的可选实现：[官方 `pyproject.toml`](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/pyproject.toml#L50-L76)。

当前 OSS 的 Memory 有明确降级策略：

- 未安装 memory extra 时，NL-SQL 记忆使用 `knowledge/sql/*.md` 上的 token/substring 检索；安装后才使用 LanceDB 做 embedding 语义检索：[官方索引后端](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/index_backend.py#L1-L13)、[后端选择](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/index_backend.py#L143-L186)。
- Schema 小于约 `30K` 字符时，官方默认直接返回完整纯文本 Schema；超过阈值才改用 embedding 检索相关片段：[官方 Memory 使用说明](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/skills_content/usage/references/memory.md#L8-L19)。
- 官方将 Schema Memory 和 Query Memory 分开存储为 `schema_items` 与 `query_history`；完整 Schema 描述本身不需要 embedding，而 Schema 搜索、NL-SQL 存储与相似问题召回才计算向量：[官方 `MemoryStore`](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L1-L28)、[索引与查询记忆](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L208-L264)、[纯文本与向量检索](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L309-L361)、[NL-SQL 相似召回](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L389-L430)。

所以“Wren 官方必须配置向量模型”只对 Classic 的完整 AI Service/RAG 部署成立；对当前 OSS 的 Wren Engine/CLI 基础查询并不成立。向量 Memory 是增强能力，不是 SQL Engine 的前置条件。

## Classic 中向量模型具体处理什么

| 数据 | 写入向量库的主要内容 | 查询时的作用 | 官方证据 |
|---|---|---|---|
| DB Schema | 表、列、主外键、关系、约束及描述等切片 | 从大 Schema 中先召回与问题相关的表和字段，再交给后续 Schema pruning/LLM | [Schema indexing](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/indexing/db_schema.py#L317-L355)、[Schema retrieval](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/db_schema_retrieval.py#L125-L200) |
| Table description | 表的业务描述 | 用自然语言业务词找到对应物理/语义表 | [Table description indexing](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/indexing/table_description.py#L96-L153) |
| Historical questions | 当前问题及相关历史问题形成的文本 | 识别相似历史询问，辅助后续意图和 SQL 生成流程 | [Historical question indexing](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/indexing/historical_question.py#L33-L62)、[Historical question retrieval](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/historical_question_retrieval.py#L58-L101) |
| SQL pairs | 自然语言问题作为向量文本，SQL 保存在 metadata | 召回相似的已确认问法与 SQL，作为 few-shot 样例 | [SQL pairs indexing](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/indexing/sql_pairs.py#L31-L47)、[SQL pairs retrieval](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/sql_pairs_retrieval.py#L56-L97) |
| Instructions | 非默认指令以其适用问题做向量文本，具体指令、scope 等保存在 metadata；全局默认指令另行无向量条件取回 | 找出与当前问题相关的业务规则、口径和限制 | [Instructions indexing](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/indexing/instructions.py#L30-L52)、[Instructions retrieval](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/instructions.py#L77-L102)、[默认指令读取](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/instructions.py#L133-L177) |

向量不是数据库行数据的通用索引，也不会把业务表全部同步进 Qdrant。上述索引保存的是辅助 Text-to-SQL 的语义上下文。数据库事实数据仍由最终 SQL 到原数据库查询。

## 它在哪个阶段生效

```text
建模或知识更新
  -> 把 Schema / 描述 / 历史问法 / NL-SQL / 指令转成 embedding
  -> 写入 Qdrant（Classic）或 LanceDB（当前 OSS 可选 Memory）

用户提问
  -> 把问题转成 embedding
  -> 相似度召回相关上下文
  -> LLM 使用“问题 + 召回上下文”生成 SQL
  -> SQL 校验、dry run / correction
  -> Wren Engine 执行 SQL
  -> 原数据库返回结果
```

Classic 的 Ask 服务先并行召回 SQL pairs 与 instructions，再做 Schema retrieval，最后调用 SQL generation：[官方 Ask 编排](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L192-L232)、[Schema 召回](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L346-L369)、[SQL 生成](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/web/v1/services/ask.py#L441-L490)。SQL 生成 prompt 接收已经选出的 Schema、SQL samples 和 instructions，而不是在 SQL executor 内调用 embedding：[官方 SQL generation](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/generation/sql_generation.py#L30-L77)、[官方 SQL executor](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/sql_executor.py#L22-L48)。

因此向量模型会**间接影响 SQL 的正确率**：召回错表、漏掉业务指令或召回错误样例，会让 LLM 生成错误 SQL；但它**不参与 SQL 的语法重写、数据库连接、执行计划或结果计算**。

## 改造前为什么表面上不需要配置

本仓库改造前的请求链是：

1. Java `WrenDatabaseTool` 把 `sourceKey`、自然语言问题、员工请求级 LLM 配置和 `expectedMdlDigest` 发给本机 Adapter：[本仓库 `WrenDatabaseTool`](../../customer/app/src/main/java/com/customer/mcp/capability/WrenDatabaseTool.java#L61-L84)。
2. Adapter 读取该数据源的完整 `manifest`，把整个 Schema 描述追加到 system prompt，并调用 OpenAI-compatible `chat/completions`。
3. Adapter 对生成 SQL 做只读校验和 lineage 校验，然后调用 `WrenRuntime.query`：[本仓库请求入口](../../customer/wren/adapter/server.py#L477-L499)。
4. `WrenRuntime.query` 直接调用 `WrenEngine.query`，并在同一锁内校验 MDL digest 和结果完整性限制：[本仓库执行路径](../../customer/wren/adapter/server.py#L194-L213)。

这条旧路径没有构造 Memory，也没有调用 embedding，所以安装器不需要 LanceDB。项目当时只复用了 Wren 的 MDL 编译、语义 SQL 规划和 connector 执行能力，而不是官方完整 AI/RAG pipeline。

当前实现已经改变：

1. Runtime 与 Control Plane 都读取完整 `/v1/models` 响应，按 `supported_endpoint_types` 分别选择生成、向量和可选重排模型，不再取数组第一项。
2. Adapter 使用官方约 `30K` 字符阈值；小 Schema 使用完整上下文，大 Schema 使用 LanceDB 召回 Schema，并按完整 MDL 补齐一跳 Relationship 与 Join 两端 Model。
3. Schema Memory 与 Query Memory 分表；Query Memory 只读取随项目发布并确认的 `knowledge/sql/*.md`，不会自动保存刚生成的 SQL。
4. `knowledge/rules/*.md` 始终完整、确定性加载，不参与可能漏召回的向量筛选。
5. 索引目录按实例根目录、`sourceKey`、`mdlDigest` 和 embedding 模型隔离；向量维度取实际 endpoint 返回值，变化时通过 staging 索引重建并切换。
6. 首次大 Schema 查询会惰性构建索引，因此可能明显慢于后续请求；当前尚未把索引预构建前移到 Release 发布事务。

## 改造前取舍与当前生产边界

改造前做法的优点是部署依赖少、一次请求看到完整 MDL，不会因向量 top-k 召回而遗漏未命中的关系。代价是：

- Schema 增大后，完整 manifest 会持续消耗 LLM context 和 token，并可能超过模型上下文上限；
- 无法语义召回已确认 NL-SQL 样例，重复复杂问题不能复用历史正确模式；
- 没有 Classic 那种按问题召回业务 instructions 的能力；
- 全量上下文中的无关表越多，越可能干扰选表和 join 判断。

出现以下任一情况时，就应把 Memory 作为独立能力引入并做真实评测：

1. 单数据源 MDL 接近或超过当前 OSS 官方采用的约 `30K` 字符切换阈值；
2. 员工 LLM 的上下文限制、延迟或 token 成本已成为问题；
3. 产品需要持久化并召回已确认的 NL-SQL 样例；
4. 产品需要从大量业务规则中按问题选择相关规则；
5. 用客户真实问题集验证后，向量召回相对完整 Schema prompt 能显著提升正确率。

用户已经确认真实客户会有几百张表，每张表十几个到几十个字段，因此本项目已经满足第 1、2 项，不再属于“可选优化”。当前实现已把索引绑定到 `sourceKey + mdlDigest + embedding model`，并在向量维度变化时重建；向量检索仍只筛选生成上下文，不能替代 Current MDL 摘要校验、只读 SQL 校验、权限审查、结果完整性限制与数据库审计。

本地自动化验证已覆盖模型能力分配、30K 混合策略、Schema/Query Memory 分离、关系补全、维度变化重建、重排降级和 LanceDB 实际读写。尚未验证真实员工 NewAPI 的 embedding/rerank endpoint、数百表客户 MDL、真实客户数据库和完整认证请求链，因此不能据此宣称生产环境端到端验收完成。

## 面向本项目的可实施契约

下面的契约借鉴 Wren 官方的索引对象、召回顺序和生命周期约束，但适配本项目“员工模型接口提供远程 OpenAI-compatible embedding”的现实。它不是声称当前 Wren OSS 已原样实现这些接口。

### 1. 按能力选择模型，禁止取模型列表第一项

员工模型接口返回的 `supported_endpoint_types` 应作为用途判定依据，而不是依赖数组顺序：

| 用途 | 必须包含的 endpoint type | 当前示例中的模型 | 选择规则 |
|---|---|---|---|
| SQL 生成 | `openai` | `灵枢玄同`、`灵枢玄同Pro` | 使用员工显式配置的 chat model；未配置时只在纯 chat 候选中按稳定规则选择，不能取列表第一项 |
| Schema / Query embedding | `embeddings` | `灵枢向量` | 使用员工显式配置的 embedding model；只有一个候选时可自动选择 |
| 二阶段重排 | `jina-rerank` | `灵枢重排` | 可选增强；没有候选、调用失败或超时时退回向量相似度顺序 |

这与 Classic 的职责拆分一致：官方把 LLM 与 embedder 配成不同 provider/model，embedder 通过 OpenAI-compatible/LiteLLM embedding 调用接收单条或批量文本，而不是复用 chat completion：[Classic 模型配置](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/docker/config.example.yaml#L1-L55)、[文本 embedding 调用](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/providers/embedder/litellm.py#L33-L76)、[批量文档 embedding](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/providers/embedder/litellm.py#L79-L162)。

模型解析结果必须在一次员工请求内冻结，至少包含：

```json
{
  "chatModelId": "灵枢玄同Pro",
  "embeddingModelId": "灵枢向量",
  "rerankModelId": "灵枢重排",
  "embeddingDimension": "<probe 返回的实际长度>"
}
```

其中 `embeddingDimension` 不能从模型名称猜测。第一次使用时应调用 embedding endpoint 对固定 probe 文本生成向量，以返回数组长度为准。Wren 当前 OSS 同样通过实际 embedding probe 得到新索引维度，并拒绝不同维度的新向量写入既有表：[维度探测](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/embeddings.py#L470-L480)、[既有索引维度校验](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L152-L200)。

### 2. Schema Memory 的索引单位与隔离键

不能把完整 MDL 作为一个向量。至少应拆成以下独立可召回单元：

- Model / 表摘要；
- Column / 字段，文本包含所属 Model、类型、业务描述、是否主键和表达式；
- Relationship，文本包含两端 Model、连接条件和 cardinality；
- View；
- 若启用 Cube，再包含 Cube、Measure、Dimension、TimeDimension。

这与当前 OSS `extract_schema_items` 的粒度一致：[Schema item 拆分](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/schema_indexer.py#L309-L360)。Classic 则先向量召回相关表，再按表名取回完整 Schema；上下文过大或启用 column pruning 时，再让 LLM 选择必要字段：[表召回与完整 Schema 回填](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/db_schema_retrieval.py#L123-L203)、[上下文大小判断与字段裁剪](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/db_schema_retrieval.py#L234-L338)。

本项目每条向量记录至少携带以下过滤字段：

```text
instanceId + sourceKey + mdlDigest + embeddingModelId + embeddingDimension
```

查询时这五项必须先做精确过滤，再计算相似度。不能只用 `sourceKey`，也不能让新 Release 召回旧 MDL 的字段。Wren 官方可对 Schema 搜索附加当前 `mdl_hash` 过滤，并在 Query Memory 中按 datasource 过滤：[Schema hash 过滤](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L313-L377)、[Query datasource 过滤](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L414-L435)。

向量初召回后必须进行结构扩展：把命中的 Model 补成必要字段，并依据完整 MDL 关系图补入可达的中间表、Relationship 和 Join 字段。向量搜索负责找入口，完整 MDL 仍负责保证关系闭包；不能把若干孤立字段直接交给 SQL LLM。

### 3. Query Memory 只保存可复用的正确 NL-SQL

Query Memory 将自然语言问题做 embedding，SQL 和数据源信息作为 metadata；查询时用当前问题召回相似 NL-SQL，作为 few-shot 示例。官方 OSS 的存储与召回正是这个结构：[NL-SQL 写入](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L381-L412)、[相似问题召回](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L414-L435)。

本项目不应把“LLM 刚生成的 SQL”立即写成可信样例。只有满足以下条件之一才可进入生产 Query Memory：

1. 管理员明确确认；
2. 员工反馈确认且 SQL 已通过只读、lineage、`mdlDigest` 和实际执行校验；
3. 来自随 Release 发布并经过验收的种子样例。

错误、被修正、执行失败或跨 Release 语义已变化的 SQL 不得继续召回。Wren 官方生命周期同样要求错误回答不要存储，并在重新索引 Schema 时替换 seed queries、保留用户确认项：[官方 Memory 生命周期](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/skills_content/usage/references/memory.md#L99-L128)、[Schema 与 seed 更新](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L208-L264)。本项目还需额外以 `mdlDigest` 隔离已确认样例，避免旧模型定义污染新 Release。

### 4. Rerank 是可选增强，不是 Wren 官方必需依赖

在本次固定提交范围内，Classic 和当前 OSS 都没有调用独立 rerank endpoint。Classic 的 SQL pairs 流程是 embedding 检索后按 similarity threshold 和 max size 截断，源码还明确留下了以后增加 LLM filter 的 TODO：[SQL pairs 检索与过滤](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/sql_pairs_retrieval.py#L55-L100)、[pipeline 组装](https://github.com/Canner/WrenAI/blob/e42b8d057c611016d781c7bbe74ba4e5aeb9712d/wren-ai-service/src/pipelines/retrieval/sql_pairs_retrieval.py#L116-L139)。因此 `灵枢重排` 是本项目可利用的额外能力，不能描述成复刻 Wren 所必需。

建议流程是先向量召回较宽候选集，再在已通过同一索引隔离键过滤的候选内重排：

```text
embedding top 30~50
  -> 可选 jina-rerank
  -> schema top 8~20 / query examples top 3~10
  -> MDL 关系扩展
```

Rerank 必须设置独立超时和熔断；失败时保持原向量排序，不能导致 SQL 查询整体不可用。候选上限、最终上限、超时、是否降级和实际使用的模型 ID 都要进入审计事件。

### 5. 索引发布必须与 Release 一起完成

官方明确要求 MDL 更新后重新索引，而不是每次问题到来前重建：[官方索引时机](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/skills_content/usage/references/memory.md#L46-L58)。当前 OSS 的 `replace=True` 会替换 Schema 表，并且模型维度改变时要求 reset 或恢复原模型：[Schema replace](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L210-L258)、[混合维度拒绝](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/memory/store.py#L165-L200)。

本项目不能直接覆盖当前生产索引，发布顺序应为：

```text
保存 Draft
  -> 生成不可变 Release 和 mdlDigest
  -> 解析员工模型列表并冻结 embeddingModelId
  -> probe 得到 embeddingDimension
  -> 在 staging index 构建 Schema Memory 和 seed Query Memory
  -> 校验条数、维度、随机召回、mdlDigest
  -> 原子切换 Active Release + Active Index
  -> 延迟回收上一版本索引
```

任何构建或校验失败都不得切换 Active Release。模型 ID、维度、归一化方式或向量生成算法任一变化，都视为新的 index generation，必须全量重建，不能把新旧向量混写。

### 6. 最终 Retrieval-to-SQL 请求链

```text
GET 员工可用模型
  -> 按 endpoint capability 解析 chat / embeddings / optional rerank
  -> 校验 Active Release、expectedMdlDigest 与 Active Index generation
  -> embedding(员工问题)
  -> 精确限定 instanceId/sourceKey/mdlDigest/model/dimension
  -> 并行召回 Schema Memory 与已确认 Query Memory
  -> 可选 rerank
  -> 依据完整 MDL 做关系闭包、Join 字段补全和上下文预算裁剪
  -> 组装“问题 + 精简 Schema + 关系 + NL-SQL 样例 + 确定性规则”
  -> chat model 生成 SQL
  -> 完整 MDL 上做 SQL 规划、只读校验、lineage、dry-run/correction
  -> Wren Engine 执行并审计
```

这保持了 Wren 的核心原则：Memory 负责在生成 SQL 前缩小上下文，完整语义模型与 Engine 负责生成后的规划和执行。当前 OSS 给出的标准顺序也是先 recall 相似问题、再 fetch Schema、再写 SQL并执行：[官方完整 Memory 流程](https://github.com/Canner/WrenAI/blob/871118e94f1525c401d867074c05e7e8eefca1cc/core/wren/src/wren/skills_content/usage/references/memory.md#L113-L128)。
