# Wren 单 JAR 部署形态调研

> 调研日期：2026-09-22  
> 本仓库 Wren 基线：`wrenai 0.14.0`，上游提交 `be1f9b57d2664aeb8287eef3eae3d931d90da3b9`  
> 官方主线核对提交：[`dcc964efe0bc8693ebabf087c587062bda79bfa1`](https://github.com/Canner/WrenAI/commit/dcc964efe0bc8693ebabf087c587062bda79bfa1)

## 一、结论

推荐继续保持客户侧“**只部署一个 JAR、只启动一个 Java 服务**”的产品体验，但不要把 Wren 重写成 customerapp 的 Java 业务模块。实现方式是：

1. 构建阶段把当前 Python Adapter、vendored `wrenai`、Python 解释器、`wren-core-py` 和选定数据库驱动冻结为**按操作系统和 CPU 架构构建的 self-contained sidecar 目录**。
2. 将该目录压缩后作为资源放入对应平台的 Spring Boot Fat JAR；customerapp 首次启动或版本变化时，按摘要解压到实例私有、持久化的运行目录。
3. customerapp 用 `ProcessBuilder` 启动、探活、记录日志和回收 sidecar。客户和运维只操作 Java 服务；内部仍是 Java 与 Python/Rust 两个进程。
4. JAR、sidecar 和第三方声明使用同一个发布版本与摘要。现有升级器切换 JAR 后，新 JAR 解压自己的 sidecar；健康失败则回滚旧 JAR，旧版本 sidecar 仍可恢复。

优先使用 PyInstaller `onedir` 产物再压入 JAR，不优先使用 PyInstaller `onefile`。`onefile` 启动时仍会把解释器和 `.so`/`.pyd` 解压到随机 `_MEIxxxxxx` 临时目录，启动更慢；`onedir` 更容易诊断，也更适合做逐文件摘要和版本缓存。来源：[PyInstaller 工作方式](https://pyinstaller.org/en/stable/operating-mode.html)。

这实现的是**单交付物、单启动入口、双进程隔离**。如果“一个 JAR”被解释为“JVM 内只能有一个进程”，则当前 Wren 技术栈不适合低成本满足；需要长期维护 Java/Rust 新实现，风险远大于收益。

## 二、当前实际技术栈

### 2.1 当前不是两个独立的 Wren 后台

本仓库生产调用链是：

```text
customerapp（Java）
  -> loopback HTTP
  -> Customer Wren Adapter（Python）
       -> WrenEngine（同一 Python 进程）
          -> wren-core-py（Rust/PyO3 原生扩展）
          -> Python 数据库 connector / PyArrow
       -> LanceDB 原生扩展
```

`WrenEngine` 不是第三个常驻服务。本仓库 Adapter 在进程内实例化 `WrenEngine`，当前数据源 connector 也由该 Python 进程直接执行；不需要旧版 Wren GenBI Classic 的 `wren-engine`、`ibis-server`、AI Service、Qdrant 等容器。仓库依据：[Adapter 运行时](../../customer/wren/adapter/server.py)、[WrenEngine](../../customer/wren/upstream/src/wren/engine.py)、[connector factory](../../customer/wren/upstream/src/wren/connector/factory.py)。官方当前架构也把 Python SDK/CLI、PyO3 `wren-core` 和 connector 作为当前路径，而不是 Classic 多服务路径，见[官方架构](https://github.com/Canner/WrenAI/blob/dcc964efe0bc8693ebabf087c587062bda79bfa1/docs/core/reference/architecture.md)。

### 2.2 不能把它当成纯 Python 代码复制进 JAR

- 官方 `wrenai` 要求 Python 3.11+，依赖 `wren-core-py`、DuckDB、PyArrow、sqlglot、pandas 等，并按数据源加载 `mysqlclient`、`psycopg`、`pyodbc` 等可选依赖。来源：[官方 pyproject.toml](https://github.com/Canner/WrenAI/blob/dcc964efe0bc8693ebabf087c587062bda79bfa1/core/wren/pyproject.toml)、[本仓库锁定清单](../../customer/wren/upstream/pyproject.toml)。
- `wren-core-py` 是 Rust `cdylib`，通过 PyO3 `extension-module` 和 `abi3-py311` 暴露给 CPython，并依赖 Wren Rust Core/DataFusion。它不是 JVM 类库。来源：[官方 wren-core-py Cargo.toml](https://github.com/Canner/WrenAI/blob/dcc964efe0bc8693ebabf087c587062bda79bfa1/core/wren-core-py/Cargo.toml)、[官方 wren-core-py pyproject.toml](https://github.com/Canner/WrenAI/blob/dcc964efe0bc8693ebabf087c587062bda79bfa1/core/wren-core-py/pyproject.toml)。
- 当前 Windows 环境实际安装的是 `wren_core/wren_core.pyd`，同时还有 DuckDB、PyArrow、LanceDB、NumPy 和 MySQL 的 `.pyd`/`.dll`。因此制品必然与 OS、CPU 架构及本机 ABI 有关，不能生成一个同时适用于 Windows/Linux、x64/arm64 的通用 JAR。
- 本仓库当前 vendored Python 主体约 71 个文件、2.18 万行，定制 Adapter 约 9 个文件、2700 行；这还不包括 Rust Core、DataFusion 和各数据库驱动。行数只用于说明迁移量级，不是质量判断。

## 三、为什么不建议重写为 Java 模块

“把 HTTP Adapter 改成 Spring Controller”只能去掉约 2700 行 Adapter 外壳，不能去掉 Python/Rust 引擎和 connector。若要求 JVM 单进程，至少还要处理：

- 将 MDL manifest 提取、SQL policy、CTE rewrite、方言转换及 Wren Rust Core 接入 JVM；
- 重做 PyArrow 结果契约、各数据源 connector、超时与 dry-run 语义；
- 重做当前 LanceDB Schema/Query Memory、embedding/rerank 降级和索引原子切换；
- 逐项追平上游安全修复、数据库兼容和 MDL 演进。

可选的 JNI/JNA 直连 Rust 也不是低成本捷径：官方只提供 Python `cdylib` 和浏览器 WASM 包，没有官方 Java binding。官方 WASM 包定位为“Browser-native semantic SQL engine”，并不能替代本项目的 Python connector、Adapter 管理接口和向量检索。来源：[wren-core-wasm package](https://github.com/Canner/WrenAI/blob/dcc964efe0bc8693ebabf087c587062bda79bfa1/core/wren-core-wasm/package.json)。

因此，只有在满足以下条件时才值得另立项目评估 Java/Rust 重写：确认长期只支持极少数数据库、冻结 MDL 能力边界、有专门团队承担上游差异，并且双进程在目标客户环境中确实不可接受。当前问题是部署体验和升级原子性，不是业务能力必须运行在 JVM 内。

## 四、方案比较

| 方案 | 客户启动入口 | 运行进程 | 跨平台 | 升级 | 主要问题 | 判断 |
|---|---:|---:|---|---|---|---|
| Java 重写全部 Wren | 1 | 1 | JVM 部分较好 | 单 JAR | 重写 Python/Rust/DataFusion/connector，长期追上游 | 不推荐 |
| JAR 内嵌 PyInstaller `onedir` 压缩包 | 1 | 2 | 每个平台单独构建 | JAR 摘要覆盖 sidecar，可原子回滚 | JAR 变大；需安全解压与进程治理 | **推荐** |
| JAR 内嵌 PyInstaller `onefile` | 1 | 2-3（含 bootloader 模型） | 每个平台单独构建 | 单文件简单 | 每次启动解压临时目录、慢、诊断和企业杀软兼容较差 | 可做 PoC，不作默认 |
| 发布包包含 JAR + sidecar 目录 | 1 个服务 | 2 | 每个平台单独构建 | 最清晰、可差分 | 字面上不再是“只有一个 JAR”，但仍是一个升级包 | 运维优先备选 |
| 自研 Rust native sidecar | 1 | 2 | 每个平台单独构建 | 可控 | 仍需重做 Adapter、connector、memory；官方无完整现成二进制 | 长期备选 |
| `jpackage` 应用镜像/安装器 | 1 | 2 | 每个平台单独构建 | 安装器升级 | 交付物更大，不是 JAR，适合桌面/完整安装 | 非当前首选 |
| Docker/Compose | 1 条命令 | 2+ | 镜像按平台 | 镜像滚动/回退成熟 | 客户需 Docker，偏离现有 JAR/systemd/计划任务升级链 | 仅容器标准客户 |

PyInstaller 明确要求针对每个目标操作系统分别构建，不是一次构建跨平台；可以用各平台 CI/虚拟机完成矩阵构建。来源：[PyInstaller 多操作系统支持](https://pyinstaller.org/en/stable/usage.html#supporting-multiple-operating-systems)。

## 五、推荐架构

### 5.1 构建与制品

按 `os-arch-python-datasourceSet` 生成 sidecar，例如：

```text
wren-sidecar-windows-x86_64-mysql/
wren-sidecar-linux-x86_64-mysql/
wren-sidecar-linux-aarch64-postgres/
```

每个目录必须来自对应目标平台的干净 CI runner，使用完整 lock/哈希安装，执行 SBOM、许可证和漏洞扫描，再由 PyInstaller `onedir` 冻结。不要在客户机运行 `pip install`，也不要依赖客户机已有 Python。数据库驱动集合按客户版本裁剪，否则制品体积和许可证面都会持续扩大。

建议的 JAR 内资源：

```text
BOOT-INF/classes/wren-sidecar/<platform>/bundle.zip
BOOT-INF/classes/wren-sidecar/<platform>/bundle-manifest.json
BOOT-INF/classes/META-INF/NOTICE-WrenAI.md
BOOT-INF/classes/META-INF/licenses/...
```

一个 JAR 只携带一个目标平台 bundle，发布名明确带平台；不要把所有平台塞进同一个 JAR。这样 JAR 的 SHA-256 同时覆盖 Java 和 sidecar，仍可沿用当前 artifact digest、下载校验和 Catalog 绑定。

### 5.2 启动与安全解压

customerapp 启动时执行：

1. 读取 bundle manifest，校验 platform/arch、Wren 版本、bundle 摘要和入口文件。
2. 在 `<instanceDir>/runtime-cache/<bundleSha256>.staging-<random>` 解压；拒绝绝对路径、`..`、符号链接和越界目标，逐文件校验摘要。
3. 设置目录/文件最小权限；Linux 只给入口执行位。完成后原子重命名为 `<bundleSha256>`，多个 JVM 同时启动时使用实例锁。
4. 状态、profiles、Current MDL、LanceDB 索引和日志继续放在版本目录外；禁止把客户凭据写入 JAR 或解压缓存。
5. 用绝对入口路径和参数数组创建 `ProcessBuilder`，显式设置工作目录、最小环境变量、loopback 地址、端口和每次启动生成的 service token。Java 官方 API保证命令、工作目录和环境由 `ProcessBuilder` 配置后启动子进程。来源：[Java 21 ProcessBuilder](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/ProcessBuilder.html)。
6. stdout/stderr 写入实例日志并持续消费，不能继续 `DISCARD`；等待 sidecar `/internal/health` 后，Java `/internal/health` 才返回 UP。

仓库已有 [WrenSidecarProcessManager](../../customer/app/src/main/java/com/customer/mcp/wren/WrenSidecarProcessManager.java)，已经实现了条件启动、启动期探活与 `@PreDestroy` 回收，可在其上演进；当前缺少内嵌制品解析、安全解压、日志保留、运行中崩溃监测/有界重启、平台校验和强制终止整棵进程树。

### 5.3 生命周期

- Java 正常退出：先停止接收新请求，再终止 sidecar，等待宽限期，最后强制回收子孙进程。
- sidecar 运行中退出：聚合健康立即 DOWN；仅对启动前/空闲期异常做有界退避重启，正在执行的请求明确失败，不能静默重放数据库查询。
- Linux：systemd 只管理 Java 服务，但服务单元要让 Java 与子进程处于同一 cgroup，并确保 stop/kill 清理整个 control group。
- Windows：需要用 Job Object 或等效 launcher 保证 Java 被强杀/机器注销时子进程不会成为孤儿；仅靠 `@PreDestroy` 覆盖不了 `kill -9`、崩溃和断电。
- 仍只绑定 `127.0.0.1`，Adapter 管理接口使用每次启动随机 token；固定默认 token 不能进入生产制品。

## 六、升级与回滚设计

现有升级器已经按 release 目录切换 JAR，并用聚合 `/internal/health` 判定成功或回滚。仓库依据：[升级说明](../../deploy/README.md)、[Linux updater](../../deploy/enterprise-mcp-updater.sh)、[聚合健康检查](../../customer/app/src/main/java/com/customer/mcp/health/RuntimeHealthController.java)。在内嵌 sidecar 后建议保持这一主链路：

```text
下载发布包 -> 校验发布包 SHA-256 -> 校验 JAR SHA-256
-> 切换新 release -> 启动新 JAR
-> 新 JAR 校验/解压自己的 sidecar -> 启动并探活
-> Java 聚合健康通过 -> 提交升级
-> 任一步失败 -> 切回旧 release/JAR -> 启动旧 sidecar
```

关键约束：

- sidecar 缓存目录使用 bundle 摘要，不使用可变的 `current` 内容；保留当前和上一版本，升级成功后再异步清理更老版本。
- 客户 state/schema 必须版本化。若新版本需要不可逆迁移，不能只回滚二进制；第一阶段只允许向后兼容或 copy-on-write 索引重建。
- 聚合健康只证明 Java 与 Adapter/Wren 可用，不证明客户数据库可查询。发布验收增加一个不泄露结果的真实 profile `SELECT 1`/`dry-run`，但是否将其作为自动回滚门槛应按数据库可用性策略配置。
- 发布包虽然仍可只含 manifest + JAR，但不同平台必须发布不同 JAR 和 SHA-256；Platform 应按 Runtime 上报的 OS/arch/connectorSet 选择制品，禁止客户端下载后自行猜测。

## 七、许可证与安全边界

- 当前官方 `core/**`（包括 Wren Python、Rust Core、Python binding 和 WASM）为 Apache-2.0；官方仓库是按路径多许可证，不能把 Classic 或未来其他目录的许可证结论套用到所有内容。来源：[官方 LICENSE 映射](https://github.com/Canner/WrenAI/blob/dcc964efe0bc8693ebabf087c587062bda79bfa1/LICENSE)、[wren-core-py manifest](https://github.com/Canner/WrenAI/blob/dcc964efe0bc8693ebabf087c587062bda79bfa1/core/wren-core-py/pyproject.toml)。
- PyInstaller 是 GPLv2 加打包商业应用例外；生成物可按应用自己的许可证分发，但仍必须遵守所有被打包依赖的许可证。来源：[PyInstaller License](https://pyinstaller.org/en/stable/license.html)。
- 发布前必须生成完整 Python/Rust/原生库 SBOM 和 NOTICE，保留 Apache 2.0 正文及版权声明；数据库驱动、OpenSSL、Arrow、DuckDB、LanceDB 等逐项审查，不能只记录 Wren 主项目许可证。
- PyInstaller 是交付工具，不是代码保密或防篡改工具。完整性依赖签名发布、JAR/bundle 摘要、受限目录权限和启动前校验；客户控制服务器时，无法靠自解压实现绝对防逆向。
- sidecar 不应从世界可写的临时目录执行；使用实例私有持久目录，校验所有文件摘要，解压时防 Zip Slip，并拒绝已存在但摘要不符的缓存。

## 八、分阶段验证门槛

### 阶段 0：冻结边界

- 确认首批目标矩阵，例如 Windows x64 + MySQL、Linux x64 + MySQL/PostgreSQL。
- 为全部 Python 依赖生成 lock + hash、SBOM、许可证清单；固定 PyInstaller 与 Python patch 版本。
- 记录当前真实查询基线：同一 MDL、同一 SQL、相同行列、错误类型、requestId 和执行时限。

### 阶段 1：sidecar 可执行制品 PoC

- 先在 Windows x64/MySQL 使用 PyInstaller `onedir`；必须覆盖 `/internal/health`、context、datasource 管理、dry-plan、dry-run、真实 query、LanceDB rebuild。
- 在无 Python、无 pip、无网络的干净 VM 运行；验证中文路径、空格路径、非管理员账户、企业杀软扫描和 24 小时稳定性。
- 对比冻结前后结果，不能只验证进程能启动。

### 阶段 2：JAR 自解压与监督

- 验证首次解压、重复启动复用、并发启动锁、损坏缓存重建、磁盘满、无执行权限、端口冲突、sidecar 启动超时和运行中崩溃。
- 验证正常停止、Java 强杀、sidecar 强杀、系统重启后无孤儿进程；日志与 requestId 可跨 Java/Adapter 关联。
- JAR 被替换或 bundle 被篡改时必须 fail closed，不能回退到 PATH 中的任意 Python。

### 阶段 3：真实升级与回滚

- 从上一生产版本远程升级到内嵌 sidecar 版本，再模拟 Adapter 启动失败、健康超时、数据库临时不可用和状态迁移失败。
- 每个失败点验证 release 链接、旧 JAR、旧 sidecar、MDL/profile/索引和端口状态；旧版本必须能恢复真实查询。
- 验证同机多实例、不同端口和不同凭据完全隔离。

### 阶段 4：跨平台发布门禁

- 在每个目标 OS/arch 的原生 runner 构建和测试，禁止把一个平台产物复制成另一个平台版本。PyInstaller 官方要求逐平台构建，见[多操作系统支持](https://pyinstaller.org/en/stable/usage.html#supporting-multiple-operating-systems)。
- Platform 根据 Runtime 平台能力选择正确制品；错误平台 JAR 必须在解压前给出明确、无敏感信息的失败原因。
- 只有真实客户数据库端到端查询、升级回退和进程清理全部通过后，才能把“单 JAR Wren 部署”标记为生产完成。

## 九、最终决策建议

短期立项应命名为“**Wren self-contained sidecar 单 JAR 交付**”，不是“Wren Java 重写”。先完成一个 Windows x64/MySQL 的 `onedir -> zip -> JAR resource -> digest cache -> ProcessBuilder` 垂直 PoC；验证真实 MDL/数据库查询和失败回滚后，再扩展 Linux 与其他 connector。

如果 PoC 暴露 PyInstaller 对 LanceDB/PyArrow/数据库驱动无法稳定冻结，再降级为“一个签名发布包包含 JAR + onedir sidecar”，仍保持客户只启动一个 Java 服务。此降级只改变文件形态，不改变架构和升级原子性，也不应倒逼一次高风险 Java 重写。
