# 单包发布与自动更新设计（一个包 = 一个程序）

> 设计日期：2026-11-10
> 目标：Platform 只推**一个**制品；客户服务器只启动**一个**程序；升级原子、可回滚、失败可诊断。
> 前置：[Wren 单 JAR 内嵌运行时实施方案](../架构设计/Wren单JAR内嵌运行时实施方案-2026-11-10.md)

---

## 一、先厘清：这条约束不需要重写引擎

"一个包 + 一个程序 + 原子升级"是**交付形态**问题，不是**实现语言**问题。

| 方案 | 一个包 | 一个程序 | 零功能损失 | 工期 |
|---|---|---|---|---|
| JAR 内嵌运行时（JEP） | ✅ | ✅ 一个 `java.exe` | ✅ | 7.6 人周 |
| 纯 Java 全重写 | ✅ | ✅ | ❌ 除非 100～150 人周 | 100+ 人周 |
| JAR 内嵌 sidecar（子进程） | ✅ | ❌ 两个进程 | ✅ | 2～4 人周 |

**所以你的发布诉求，正好落在第一行。** 纯 Java 能满足"一个包"，但它满足不了"零功能损失 + 可控工期"，而发布链路本身并不因此变简单——升级脚本该做的事一件不少。

### 2.2 六处硬断点（这才是"残缺"的实体）

| # | 断点 | 证据 | 后果 |
|---|---|---|---|
| **B1** | **JAR 形态参数契约不匹配**：Runtime 只传 3 个参数，脚本强制要求 `--instance-id` | `McpUpgradeController.java:63-66` vs `enterprise-mcp-updater.sh:21` | 脚本 `usage; exit 2`；而 Tenant 已收到 202、用户已看到"升级任务已提交"——**彻底静默失败** |
| **B2** | **JAR 形态权限不可能满足**：脚本要求 root，服务以 `User=enterprise-mcp-$INSTANCE_ID` + `NoNewPrivileges=true` 运行 | `enterprise-mcp-updater.sh:20` vs `enterprise-mcp-bootstrap.sh:99,105` | 即使补上 B1 也会在 root 检查处退出 |
| **B3** | **默认脚本路径从未被安装** | `application.yml:61` 指向 `/usr/local/libexec/enterprise-mcp-updater.sh`，但 `bootstrap.sh` 从不安装到该目录 | `ProcessBuilder.start()` 抛 `IOException` → 500 → Tenant 提示"提交失败" |
| **B4** | **`installed_version` 无人写入** | `TenantMcpServerMapper.xml:54-72` 只有 insert/update 平台字段与健康，**无任何 UPDATE installed_version** | `hasUpdate` 恒为 true，升级成功后"发现新版本"永不消失 |
| **B5** | **升级结果无回读** | `McpUpgradeController` 只有 POST，无 `GET /internal/upgrades/{id}`；容器侧 `upgrade-state.json` **全仓无读取方** | 用户看不到进度/失败原因，只能刷新页面猜 |
| **B6** | **`artifactDigest` 自校验在生产形态永远空转** | `bootstrap.sh:102` 的 `ExecStart` 只传 tenant-id/instance-id，`application.yml:73` 默认空 → `RuntimeArtifactDigest.java:191-198` 直接跳过 | 摘要只用于向云端"上报身份"，从不校验"我是不是我以为的那个包" |

### 2.3 一个必须先解决的结构性矛盾：发布形态分叉

| | 容器形态（当前 Platform **唯一接受**） | JAR 形态（文档主推、`deploy/` 完整） |
|---|---|---|
| Platform 校验 | `manifestVersion==3 && artifactType=="DOCKER_IMAGE"`（`McpContainerPackageValidator.java:156-160`） | **会被拒**，校验器无 jar 分支 |
| 包内结构 | 恰好 `manifest.json` + `enterprise-mcp-image.tar` | `manifest.json` + `*.jar`（`deploy/manifest.example.json` 仍是 v1 `jarName`） |
| 升级器 | `queue-container-upgrade.sh`（参数**恰好**只有 `--download-url/--version/--sha256`，与 B1 不冲突） | `enterprise-mcp-updater.sh`（额外要求 `--instance-id` 与 root） |
| 运行期分支点 | `ENTERPRISE_MCP_UPDATER_COMMAND` 环境变量（`Dockerfile:58` vs `application.yml:61`） | 同左 |

**这意味着**：你要的"一个 JAR"，今天**根本发不上去**——Platform 只认 Docker 镜像 tar.gz。
所以"单 JAR"这件事的第一步不是改引擎，而是**在 Platform 侧增加 JAR/BUNDLE 制品类型**。

> 另注：`plt_tenant_mcp_release` 的唯一键是 `(mcp_server_id, version)`（`V1__init_platform_tables.sql:267`），
> 表里也没有 `platform/arch`。这意味着**同一版本无法同时存在 amd64 与 arm64 两个产物**，
> 多平台下发在数据库层就被禁止。内嵌运行时恰好是平台相关的，这条必须先改。

### 2.4 缺口重编（替换初版 G1–G8）

| 新编号 | 缺口 | 归属 | 说明 |
|---|---|---|---|
| G1' | Platform 不接受 JAR 制品（校验器/DB/sync 均无类型与平台维度） | Platform + 契约 | 单 JAR 的前置阻塞项 |
| G2' | `plt_tenant_mcp_release` 无 `platform/arch`、无 `imageId`、无 `runtime` 摘要；唯一键阻止多架构 | DB | `ValidatedPackage` 校验出 5 个字段只用 1 个 |
| G3' | 下载接口无元数据、无鉴权、不筛状态 | Platform | 草稿包可按 id 匿名下载 |
| G4' | 发布不可逆：无回滚/下架/灰度/审批 | Platform | 与 `私有部署能力设计.md:182` 的承诺相反 |
| G5' | 推送无 outbox/重试，Tenant 抖动即发布失败 | Platform | 与控制面共享同一事务 |
| G6' | Runtime 执行端 B1/B2/B3 三个断点 | Runtime | JAR 形态结构性不可用 |
| G7' | 状态回流缺失（B4/B5） | Tenant + Runtime | 用户侧完全无反馈 |
| G8' | `artifactDigest` 自校验空转（B6） | Runtime | 包与 manifest 不一致无法发现 |
| G9' | 断点续传 / 磁盘预检 / 预解压 / 组件级健康 / Windows 脚本 | 脚本 | 体积变大后从"可选"变"必须" |

### 2.5 值得保留的正确设计（别在改造中弄丢）

1. **版本号来自包内 manifest，不来自人工输入**——避免"填错版本"这类事故，比桌面客户端链路更严谨。
2. **流式摘要 + 恰好两条目**——4GB 包不占内存，且天然阻断路径穿越/符号链接。
3. **发布与下发同事务**——宁可发布失败，也不出现"库里生效、Tenant 没收到"。
4. **HMAC 派生 token，不落库**——Tenant↔Runtime 鉴权做得比周边链路都好。
5. **容器形态的 `flock` + 镜像 ID 比对 + 改名回滚**——JAR 形态应照抄这套语义。

## 三、制品定义：一个 JAR，manifest v2

### 3.1 发布物

```text
enterprise-mcp-1.1.0-linux-x86_64.jar     # 唯一交付物（含运行时资源）
manifest.json                              # Platform 记录 + 下发用（不进 JAR）
```

平台侧只存两类东西：**JAR 本体** + **manifest**。客户只下载 JAR，manifest 由 Platform 在触发升级时下发给 Tenant（或由 Tenant 转给 Runtime），避免"两个包"的误解——manifest 是元数据，不是第二个交付物。

### 3.2 manifest v2

```json
{
  "schemaVersion": 2,
  "platformMcpId": 20001,
  "instanceId": "tenant-10000-mcp-20001",
  "version": "1.1.0",
  "platform": "linux-x86_64",
  "artifact": {
    "name": "enterprise-mcp.jar",
    "sha256": "…",
    "sizeBytes": 312000000
  },
  "runtime": {
    "bundle": "wren/linux-x86_64",
    "bundleSha256": "…",
    "python": "3.12.10",
    "jep": "4.3.2",
    "wrenCore": "0.8.0",
    "wrenai": "0.14.0",
    "sqlglot": "30.18.0"
  },
  "health": {
    "type": "HTTP",
    "path": "/internal/health",
    "expectedStatus": 200,
    "requireComponents": ["runtime", "wren"],
    "requireEngineReady": true
  },
  "minDiskBytes": 1200000000,
  "releasedAt": "2026-11-10T14:00:00Z"
}
```

设计要点：

- `platform` **必填**。内嵌运行时按平台构建，平台必须按 Runtime 上报的 `os/arch` 选包，禁止客户端猜测。
- `runtime` 段是**溯源信息**，不是第二个下载物；JAR 启动时会用它和 JAR 内 `runtime.json` 交叉校验，不一致直接 fail closed。
- `requireEngineReady` 让健康门禁穿透到引擎（见 §5）。
- `minDiskBytes` 用于预检，避免解压到一半撑爆。

### 3.3 向后兼容

- `schemaVersion: 1`（现有 manifest）继续可读：`platform` 缺省 `linux-x86_64`、`runtime` 缺省 null、`requireEngineReady` 缺省 false。
- updater 按 `schemaVersion` 分支，不要求客户同时升级脚本。

## 四、Platform 侧：在已有发布作业上扩展（不是从零做）

> 修正：初版写"新增发布流水线"是错的。`TenantMcpController` + `TenantMcpService` + `ClientReleaseStorageService` + `McpContainerPackageValidator` 已经覆盖了
> "上传 → 校验 → 落 OSS → 登记 → 发布 → 推送 Tenant/Control Plane" 的全链路。
> **真正要做的是让它接受 JAR 制品，并把校验成果落库下发。**

### 4.1 需要改的四处（而不是全部重写）

| # | 改动点 | 位置 | 内容 |
|---|---|---|---|
| A1 | 校验器增加 JAR/BUNDLE 分支 | `McpContainerPackageValidator.validate`（`:63-71`） | 按 `artifactType` 分派：`DOCKER_IMAGE` 走现有逻辑；`SINGLE_JAR` 校验「恰好两条目：`manifest.json` + `*.jar`」、jar 摘要、jar 内 `runtime.json` 的 platform 与 manifest 一致 |
| A2 | 校验成果落库 | `ClientReleaseStorageService.java:155`（当前只取 `version()`） | 把 `ValidatedPackage` 的 `platform`、`archiveSha256`、`imageId`（或 `bundleSha256`）一并写入 DB |
| A3 | 表结构扩展 | `V1__init_platform_tables.sql:249-269` + 新 migration | 增加 `artifact_type`、`platform`、`arch`、`bundle_sha256`、`build_time`；**唯一键改为 `(mcp_server_id, version, platform)`** |
| A4 | 下发字段扩展 | `PlatformMcpSyncItem.java:16-31` | 增加 `platform`、`fileSize`、`bundleSha256`；Tenant 侧同步 DTO 同步扩展 |

### 4.2 构建侧（新增，但很薄）

```text
① 构建（目标平台 runner）
     mvn -pl customer/app -am package
     → 生成 runtime.zip（该平台）+ 打进 JAR
② 计算
     jarSha = sha256(jar)          # 由构建脚本产出，不手工填
     bundleSha = sha256(runtime.zip)
③ 门禁
     java -jar --selftest 退出码 0（见 §6.2）
     pom.version == manifest.version == JAR 内登记 artifact-version
④ 打成 Platform 接受的两条目 tar.gz（复刻 build-container-package.sh 的做法）
⑤ 走已有上传接口（`POST /admin/tenant-mcp/release/draft`）
⑥ 走已有发布接口（`POST /admin/tenant-mcp/release/{id}/publish`）
```

**注意**：`build-container-package.sh` 已经把"生成 manifest + 两条目 tar.gz"这套做法跑通了，
JAR 形态只需把 `enterprise-mcp-image.tar` 换成 `enterprise-mcp.jar`，不需要另写一套打包器。

### 4.3 顺带必须修的两个发布端缺陷（与 JAR 无关，但会直接坑你）

1. **`saveDraft` 先传 OSS 再 insert**（`TenantMcpService.java:165-187`）：insert 失败会留 OSS 垃圾；
   同版本重传会**覆盖已存在对象的字节**。→ 改为"先写库占位（PENDING）→ 上传 → 回写摘要"，或上传到 `.staging-` 前缀后再 move。
2. **下载接口不校验状态**（`TenantMcpService.java:224-230`）：草稿包可按 id 下载。→ 至少限制 `release_status=2`，
   并显式标注鉴权（当前既无 `@AllowAnonymous` 也无 `@RequireLogin`，靠拦截器默认放行）。

## 五、客户侧：升级流程（补 G9'/B1-B3）

```text
1. 预检
   - 平台匹配：manifest.platform == uname -sm 映射值，否则拒绝
   - 磁盘：可用空间 >= minDiskBytes
   - 版本：与当前版本不同；目标版本目录不存在（存在则走回滚路径）
2. 下载（断点续传）
   curl -fL -C - --retry 5 --retry-delay 5 --connect-timeout 15 \
        --max-time $((sizeBytes / 51200 + 600)) -o pkg.jar "$downloadUrl"
3. 校验 sha256（包）
4. 安装到新 release 目录，校验 jar 内 runtime.json 与 manifest.runtime 一致
5. 预解压运行时（关键新增）
   java -jar <new>/enterprise-mcp.jar --wren-extract-only
   → 失败则直接中止，不动 current 链接（此时服务仍在跑旧版本）
6. 切换 current → 重启 → 健康门禁
7. 失败：切回 previous → 重启 → 保留现场（日志 + 残留目录标记）
8. 成功：保留 current 与 previous 的 runtime，清理更早的（GC）
```

**第 5 步（预解压）是本方案最重要的改动**：把"解压 300MB 运行时"从首次启动挪到安装期。

- 好处：启动不会因解压卡住而被健康门禁判死；解压失败发生在"还没切链接"阶段，服务零中断。
- 代价：安装期变长（约 10～30s），但这是可预期的一次性成本。

### 5.1 健康门禁必须穿透引擎（补 G9'）

现在的判定是"HTTP 200"。合并成单进程后，必须改成**组件级判定**：

```json
GET /internal/health
{
  "status": "UP",
  "components": {
    "runtime": {"status": "UP", "enabled": true},
    "wren":    {"status": "UP", "enabled": true},
    "engine":  {"status": "UP", "enabled": true,
                "detail": {"python": "3.12.10", "wrenCore": "0.8.0",
                           "sources": 2, "models": 54, "mdlDigest": "…"}}
  }
}
```

updater 的判定改为：

```bash
jq -e '.status=="UP" and (.components.wren.status=="UP" or (.components.wren.enabled|not))' <<<"$body"
```

`engine` 组件必须来自**一次真实的桥调用**（`dispatch("/internal/health")`），而不是"Spring 上下文启动成功"。否则"Python 加载失败但 JVM 活着"会被判健康——这是本轮改造最危险的假阳性。

### 5.2 运行时缓存与回滚原子性（补 G9'）

```text
/var/lib/enterprise-mcp/<instance>/
  runtime/<bundleSha256>/        # current 与 previous 各自一份，互不影响
    python/ site-packages/ adapter/ lib/
  runtime/.staging-<rand>/       # 解压中间态，失败即删
```

- 缓存键是 **bundle 摘要**，不是版本号：运行时没变时，升级复用同一目录，零解压。
- 回滚只切符号链接，**不碰缓存**，因此回滚必然可用（这是把缓存放在 release 之外的原因）。
- GC 规则：保留 `current` 与 `previous` 引用的两个摘要，其余在成功升级 10 分钟后异步删除。

### 5.3 Windows（补 G9'）

新增 `deploy/windows/enterprise-mcp-updater.ps1`，与 sh 版**同一套步骤与判定**：

| 步骤 | Linux | Windows |
|---|---|---|
| 服务 | systemd 单元 | Windows 服务（`sc.exe`，NSSM 或 `winsw`） |
| 切换 | `ln -sfn` + `mv -Tf` | 目录 `junction` 或"重命名目录 + 改服务 BinaryPath" |
| 健康 | `curl` | `Invoke-WebRequest -TimeoutSec` |
| 断点续传 | `curl -C -` | `BITS` 或 `HttpClient` + Range 头 |

> 若客户 Windows 部署量少，也可明确"Windows 只支持手工替换 JAR + 重启计划任务"，但必须写进交付边界，不能默认支持。

## 六、体积带来的现实约束（必须提前告知客户）

### 6.1 下载时间

| 带宽 | 312MB 下载耗时 | 现有 `--max-time 600` 是否够 |
|---|---:|---|
| 100 Mbps | ~25 s | 够 |
| 20 Mbps | ~125 s | 够 |
| 10 Mbps | ~250 s | 勉强 |
| 5 Mbps | ~500 s | **临界** |
| 2 Mbps | ~1250 s | **必失败** |

结论：`--max-time` 必须按包大小动态计算（`sizeBytes/50KBps + 600s`），并支持 `-C -` 续传。

### 6.2 首次启动自检

新增 CLI 参数（不启动 Web 服务）：

```bash
java -jar enterprise-mcp.jar --selftest
# 校验：runtime 解压完整 → libjep 可加载 → SharedInterpreter 可创建
#       → import wren_core/sqlglot → dispatch("/internal/health") 返回 UP
# 输出：单行 JSON + 退出码
```

用途：Platform 发布门禁（§4 第 ③ 步）、客户侧预解压（§5 第 5 步）、故障诊断。

### 6.3 磁盘

解压后约 700MB；两版本共存 + 两个运行时缓存 → 建议客户预留 **2GB**。`minDiskBytes` 预检拦在这之前。

## 七、失败矩阵

| 步骤 | 失败后果 | 自动恢复 | 人工可见性 |
|---|---|---|---|
| 平台不匹配 | 拒绝安装 | 无（保持旧版运行） | 明确错误："包平台 linux-x86_64，本机 linux-aarch64" |

| 回滚时旧缓存被误删 | 回滚不可用 | 禁止（GC 只看引用） | GC 日志 |

## 十、结论

1. **Platform 发布作业已经存在**，而且校验层（恰两条目、流式摘要、身份、平台白名单、健康契约）做得比周边链路都扎实——这部分不要重写，只需要扩展。
2. **真正卡住的是两件事**：
   - **形态分叉**：Platform 只接受 `manifestVersion 3 / DOCKER_IMAGE` 的镜像包，你要的单 JAR 今天**发不上去**；
   - **最后一公里断了**：JAR 形态的升级链在「参数 / 权限 / 脚本路径」三处同时断裂，且升级结果从不回流（`installed_version` 无人写）。
3. 所以顺序应该是：
   **先修 B1–B3（约 1.2 人周）让升级真的能跑 → 再补 B4/B5（约 1.2 人周）让结果看得见 → 最后扩展 Platform 支持 JAR（约 1.8 人周）**。
4. 引擎改造（7.6 人周）排在发布形态确定之后——否则做完了也发不出去。两者在 `--selftest` 这个接口上汇合。
5. 一句话：**你的发布系统不是"没做"，是"做完了 80% 然后停在最后一百米，而且停的那一百米恰好是 JAR 形态专属的"。**
