# Wren 单 JAR 内嵌运行时实施方案

> 决策日期：2026-11-10
> 用户硬约束（全部为必须满足）：
> 1. **一个 JAR**，由 customerapp 作为依赖引入，不对外多一个交付物；
> 2. **不阉割 Wren 任何功能**；
> 3. **保证 Wren 能生成任何 SQL**；
> 4. **customerapp 的 Wren 管理界面正常可用，能调用 Wren 的任何接口**。
> 前置：[Wren 转 Java 重写可行性评估](../调研评估/Wren转Java重写可行性评估-2026-11-10.md)、[单进程语义引擎实现方案](单进程语义引擎实现方案-2026-11-10.md)

---

## 一、结论

**同时满足这四条，只有一种架构：把现有运行时（CPython + `wren_core` + `sqlglot` + connector）打进 JAR，在 JVM 进程内通过 JEP 加载并调用。**

即：**一个 JAR、一个进程、一份未改动的引擎**。

```text
customer-enterprise-mcp-1.0.0.jar
└── BOOT-INF/classes/wren/
    ├── <platform>/runtime.zip      # CPython 3.12 + site-packages + adapter + libjep
    └── <platform>/runtime.json     # 版本、平台、逐文件摘要
```

启动时解压到实例私有目录，`System.load(libjep)`，`new SharedInterpreter()`，然后调 Python 的 `dispatch(method, path, body)`。

**为什么这不是"折中"，而是唯一解**：见 §2 的数据。

---

## 二、为什么"纯 Java"与"任何 SQL + 零功能损失"不可兼得

这不是能力问题，是规模问题。要满足"任何 SQL"，必须复刻两样东西：

| 组件 | 实测规模 | 性质 |
|---|---|---|
| `sqlglot` | 183 个文件、**10,933 行**、**35 个方言** | 解析 + 生成 + 优化器（`qualify_columns`）+ 血缘，JVM 无等价物 |
| `wren-core` | 128MB 原生扩展（Rust + DataFusion） | MDL 语义展开、表达式、cube/metric、CLAC/RLAC、函数注册 |
| connector | 20+ 数据源 | 每种的类型映射、分页、EXPLAIN 语义 |

而且这 10,933 行只是"代码量"，真正的成本在**边界行为**：同一句 SQL 在 35 个方言下的引号、折叠、函数名、分页写法差异。

我们的三次实测已经证明这不是理论问题：

- `DATE_TRUNC('month', created)` 在 MSSQL/PG 原样输出，在 **MySQL 被改写为 `STR_TO_DATE(CONCAT(YEAR(...)...))`**；
- 关系不进引擎（只进提示词与索引），但**计算列会**，且必须按方言翻译；
- 视图 `statement` 原样注入，但它引用的模型要先展开。

**换句话说**：任何"纯 Java 重写"要么放弃这些能力（违反约束 2/3），要么重写 DataFusion 级语义 + 35 方言（估算 100～150 人周，且永久追不上上游）。

> 参考数据点：Wren 官方曾经有过 Java 实现（`Canner/wren-engine` 的 `wren-core-legacy`，Java 21 + Airlift + Trino parser），**已被 Rust 版替换并归档**。上游自己都没能在 Java 上维持这套语义。

**所以本方案不重写引擎，只重写"外壳 + 打包 + 进程模型"**，把两个进程压成一个、把两个交付物压成一个 JAR。

## 三、架构

### 3.1 运行形态

```text
┌─────────────────────────── java.exe (唯一 OS 进程) ───────────────────────────┐
│ Spring Boot (customerapp)                                                     │
│   MCP Tool ──► WrenDatabaseTool ──► SemanticEngine ──┐                        │
│   Admin UI  ──► /internal/wren/admin/** ──► BFF ─────┤                        │
│                                                      ▼                        │
│                                             WrenBridge (JEP/JNI)              │
│                                                      │  in-process 调用        │
│                                                      ▼                        │
│                              CPython 3.12 (libpython 已加载)                  │
│                                wren.adapter.dispatch()                        │
│                                  ├─ WrenRuntime → wren_core (Rust/PyO3)       │
│                                  ├─ CTERewriter → sqlglot                     │
│                                  ├─ AdminService（建模/内省/备份）             │
│                                  └─ connector（pyodbc/psycopg/mysqlclient）   │
└───────────────────────────────────────────────────────────────────────────────┘
```

- **没有 loopback HTTP、没有 8091 端口、没有 service token、没有孤儿进程**。
- 引擎代码、MDL 语义、方言翻译 **一行不改**，因此"任何 SQL"天然成立。
- 管理界面走的还是同一套 `AdminService` 方法，因此"任何接口"天然成立。

### 3.2 Maven 模块

```text
enterprise-mcp/
├── customer/wren-runtime          # 新增：Java API + 平台运行时资源（被打进 app）
│   ├── pom.xml
│   └── src/main/
│       ├── java/com/customer/mcp/wren/runtime/
│       │   ├── WrenRuntimeAutoConfiguration.java
│       │   ├── WrenBridge.java            # JEP 生命周期 + 调用
│       │   ├── WrenInterpreterPool.java   # 解释器池（每线程一个）
│       │   ├── WrenRuntimeExtractor.java  # 解压 + 校验 + 原子切换
│       │   ├── WrenProperties.java        # 现有配置迁移
│       │   └── WrenBridgeException.java   # 错误码映射
│       └── resources/wren/<platform>/
│           ├── runtime.zip                # 构建期生成
│           └── runtime.json
└── customer/app                    # 只加一个 dependency + BFF 改直连
```

`customer/app` 侧改动极小：

```xml
<dependency>
  <groupId>com.customer</groupId>
  <artifactId>wren-runtime</artifactId>
</dependency>
```

`WrenAdminController`、`WrenDatabaseTool` 的 **HTTP 路径、请求体、响应体、409/401/404 语义全部不变**，只把 `WrenSidecarClient` 的实现从 `RestClient` 换成 `WrenBridge`。

## 四、Python 侧唯一的改动：路由 dispatch 化（约 200 行）

现在 `server.py` 把路由写在 `do_GET` / `do_POST` / `_dispatch_admin_mutation` / `_dispatch_admin_post` 里。为了"任何接口都能调"且**不重复实现一遍路由**，把它抽成一个不依赖 `BaseHTTPRequestHandler` 的分发器：

```python
# customer/wren/adapter/dispatcher.py（新增）
class Dispatcher:
    """与传输无关的唯一入口：与 HTTP 路由一一对应。"""

    def dispatch(self, method: str, path: str, query: dict[str, list[str]],
                 body: bytes, headers: dict[str, str]) -> tuple[int, bytes]:
        """返回 (status, json_bytes)；语义与现在 _respond/_respond_exception 完全一致。"""
```

`server.py` 变成薄壳：

```python
def do_POST(self):
    status, payload = DISPATCHER.dispatch("POST", path, query, raw_body, headers)
    self._write_raw(status, payload)
```

好处：

- **路由只有一份**。Java 桥调 `dispatch` 就等于调任意接口，不存在"漏实现某个端点"的可能。
- 现有 62 个测试仍然有效（它们测的是 `WrenRuntime`/`AdminService`/校验函数，不构造 `Handler`）。
- 开发期仍可 `python -m` 起 HTTP（对拍用），也可以作为 `subprocess` 逃生模式。

**这一步是整个方案"不阉割"的制度保证**：功能面不变，因为代码没换。

## 五、Java 侧桥（JEP）

### 5.1 依赖

```xml
<dependency>
  <groupId>org.ninia</groupId>
  <artifactId>jep</artifactId>
  <version>4.3.2</version>
</dependency>
```

JEP 4.3.2（2026-08）支持 **Python 3.10–3.14 + JDK 8–21**，与 `wren_core` 的 `abi3-py311` 兼容。
关键：因为有 `pyarrow`/`duckdb`/`pyodbc` 这类**不支持子解释器**的 C 扩展，必须用 **`SharedInterpreter`**，而不是 `SubInterpreter`。

### 5.2 初始化顺序（顺序错就起不来）

```java
// 1. 解压运行时（幂等，按摘要复用）
Path runtime = extractor.ensureExtracted(bundle);   // <instance>/runtime/<sha256>/

// 2. 加载 JEP 原生库（必须在创建解释器之前）
System.load(runtime.resolve("lib/libjep." + osLibSuffix()).toString());

// 3. 告诉 CPython 它的家在哪
String prevHome = System.getProperty("python.home");
System.setProperty("python.home", runtime.resolve("python").toString());

// 4. 初始化参数：禁止用户 site、禁写 pyc、UTF-8 模式
PyConfig config = new PyConfig();
config.setPythonHome(runtime.resolve("python").toString());
config.setModuleSearchPaths(List.of(
        runtime.resolve("python/lib/python3.12").toString(),
        runtime.resolve("python/lib/python3.12/lib-dynload").toString(),
        runtime.resolve("site-packages").toString(),
        runtime.resolve("adapter").toString()));
config.setNoUserSiteDirectory(1);
config.setWriteByteCode(0);
MainInterpreter.setInitParams(config);

// 5. 建池（每个线程独占一个解释器）
pool = new WrenInterpreterPool(size, () -> {
    SharedInterpreter i = new SharedInterpreter();
    i.eval("import sys, os; os.environ.setdefault('WREN_PROJECT_ROOT', " + q(projectRoot) + ")");
    i.eval("from wren.adapter.dispatcher import Dispatcher; _d = Dispatcher()");
    return i;
});
```

Windows 额外要求：在解释器内 `os.add_dll_directory(<runtime>/python)` 与 ODBC 驱动目录，否则 `import pyodbc` 会找不到 `libodbc`。

### 5.3 调用

```java
public BridgeResponse call(String method, String path, Map<String, List<String>> query, byte[] body) {
    Interpreter i = pool.borrow();               // 独占，归还前不共享
    try {
        PyObject fn = i.getValue("_d").invoke("dispatch", method, path, query, body, headers);
        int status  = (int) fn.getItem(0).__tojava__(Integer.class);
        byte[] json = (byte[]) fn.getItem(1).__tojava__(byte[].class);
        return new BridgeResponse(status, json);
    } catch (JepException e) {
        throw WrenBridgeException.fromPython(e);  // 未捕获异常 → 500 + 结构化错误
    } finally {
        pool.release(i);
    }
}
```

**错误语义零改动**：Python 的 `_respond_exception` 已经产出 `{ok, code, message, data, requestId}` + HTTP status；桥把 status 与 body 原样透给 Controller，现有 409/401/404 映射代码不动。

### 5.4 线程与并发

- `SharedInterpreter` 不能被多线程同时使用 → 用 `ArrayBlockingQueue<Interpreter>` 做池。
- 池大小默认 `max(2, min(4, cores))`。**不要开大**：现有 `WrenRuntime` 内部本来就用一把 `RLock` 串行化"摘要校验 + 查询 + MDL 切换"，Python 侧并发度不会因为池大而提升。
- 数据库 I/O 期间 CPython 释放 GIL，因此慢查询不会阻塞其他解释器线程。

## 六、打包：一个 JAR 怎么装下运行时

### 6.1 资源布局

```text
BOOT-INF/classes/wren/linux-x86_64/runtime.zip
BOOT-INF/classes/wren/linux-x86_64/runtime.json
```

`runtime.json`：

```json
{
  "platform": "linux-x86_64",
  "python": "3.12.10",
  "jep": "4.3.2",
  "wrenai": "0.14.0",
  "wrenCore": "0.8.0",
  "bundleSha256": "…",
  "files": { "python/bin/python3.12": "sha256:…", "...": "..." }
}
```

### 6.2 构建（每平台一次，与现有 Dockerfile 的 `wren-build` 阶段同源）

```bash
# 在目标平台的干净 runner 上：
python3 -m venv build/venv
build/venv/bin/pip install --require-hashes -r adapter/requirements.lock
build/venv/bin/pip install "wren-core-py==0.8.0" "lancedb==0.38.0"
# 裁剪：删除 test/__pycache__/*.dist-info/RECORD、无用 extras
# 打入 jep：pip install jep==4.3.2（含 libjep）
# 生成 runtime.zip + runtime.json
```

**不要在客户机 pip install**（与现有安装器一致）。运行时按平台各构建一份，**一个 JAR 只带一个平台**，发布名带平台后缀。
不许把三个平台塞进同一 JAR——那会让 JAR 变成 1GB 级，且校验失去意义。

### 6.3 解压

```text
<instanceDir>/runtime/<bundleSha256>/
    python/         # CPython 完整目录（含 stdlib、DLL）
    site-packages/
    adapter/        # wren/adapter/*.py（dispatch 化后）
    lib/libjep.so|dll
    .ready          # 全部校验通过后才写
```

规则（与《Wren 单 JAR 部署形态调研》§5.2 一致，直接复用）：

1. 拒绝绝对路径、`..`、符号链接、越界目标；
2. 逐文件校验摘要；
3. 解压到 `.staging-<random>`，完成后原子 rename；
4. 已存在且校验通过则直接复用（升级不改这一层）；
5. 多实例并发启动用实例锁；
6. 失败 fail closed，**不回退到 PATH 里的任何 Python**。

### 6.4 体积与升级

- JAR 预计 **250～350MB**（pyarrow + duckdb + lancedb + libpython + stdlib）。
- 需要确认三件事：私服上传大小限制、`enterprise-mcp-updater.sh` 的下载超时与断点续传、客户磁盘余量（解压后翻倍 ≈ 700MB）。
- 升级策略不变：新 JAR 带新 `bundleSha256` → 解压新目录 → 探活 → 成功后异步清理旧目录（保留上一版）。

## 七、管理界面与"任何接口"如何保证

| 关注点 | 保证方式 |
|---|---|
| UI 不改 | `WrenAdminController` 的路径、请求体、响应体、错误码全部保持；只把内部 `RestClient` 换成 `WrenBridge` |
| 任何接口可调 | Java 桥直接调 `Dispatcher.dispatch(method, path, body)`，**路由表只有 Python 一份**，不存在漏实现 |
| 409/401/404 语义 | `_respond_exception` 原样产出 status + code，桥透传 |
| 备份/恢复 | `AdminService.create_backup/restore_backup` 原方法，zip 二进制经 `byte[]` 透传 |
| 内省长任务 | `jobs/` 语义不变；`Dispatcher` 仍返回 202 + jobId |
| 建模范式 | `candidateToken` + `commit(expectedMdlDigest)` 不变，仍由 control-plane 确认 |
| 会话/鉴权 | 现有 `WrenAdminSessionService` 不变（它本来就是 Java 侧） |

**这一步的收益**：原来"UI → Java BFF → HTTP → Python"三段，变成"UI → Java BFF → 进程内调用"两段，UI 完全无感。

## 八、运行模式：默认进程内，保留逃生门

```yaml
enterprise:
  wren:
    mode: ${ENTERPRISE_MCP_WREN_MODE:inprocess}   # inprocess | subprocess
```

- `inprocess`（默认）：§3 的架构，一个进程。
- `subprocess`：**同一个 JAR、同一份 runtime.zip**，用 `ProcessBuilder` 从解压目录拉起 `python -m wren.adapter.server`，走 loopback。零额外交付物，用于"客户库极大、不接受 JVM 被拖死"或"排查 JEP 问题"的场景。

两种模式共用 `SemanticEngine` 契约，切换只改一个环境变量。这不是骑墙，是**崩溃隔离的保险丝**——见 §9 R5。

## 十一、诚实的能力与代价清单

**得到**：

- 一个 JAR、一个进程、一份引擎；零功能损失；任意 SQL；管理界面零改动；任何接口可调。
- 移除：8091 端口、service token、孤儿进程、双进程启动时序、跨进程 requestId 拼接。
- 启动更快（无 Python 进程冷启动 + 无 HTTP 握手）。

**付出**：

1. **JAR 250～350MB**，升级下载与私服存储要重新评估。
2. **仍然需要 OS 级 ODBC 驱动**（SQL Server 场景）。这是 Python connector 的现实，纯 Java 重写才能去掉——但纯 Java 做不到"任何 SQL"。这条必须写进交付说明。
3. **崩溃隔离变弱**：进程内 segfault = 服务挂。用重启策略 + `subprocess` 逃生门兜。
4. **JEP/Python 版本绑定**：升级 CPython 要重编 JEP，需纳入发布检查清单。
5. **调试路径变短但变深**：没有跨进程边界，但栈会同时出现 JVM 与 CPython 帧。

## 十四、与前一版方案的关系

前一版《单进程语义引擎实现方案》主张"用 Java 重新实现窄语义子集"，在本轮约束下**已失效并标记废弃**，原因：

- 它依赖"关系/计算列/视图可以砍掉"，与"不阉割"冲突；
- 它无法承诺"任何 SQL"，因为方言翻译层被放弃了。

本方案保留 `semantic-api` 的 SPI 设计（那一层仍然值得做，用于 `inprocess/subprocess` 双模式与未来替换），但**不重写引擎实现**。
