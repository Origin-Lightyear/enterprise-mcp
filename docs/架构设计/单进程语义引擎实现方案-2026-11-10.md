> 前提：`customerapp` 单 JVM 进程，不再启动 Python sidecar
> 上游依据：[Wren 转 Java 重写可行性评估](../调研评估/Wren转Java重写可行性评估-2026-11-10.md)

## 一、本方案的核心判断

评估文档说"L5 方言重写 + L6 语义展开是研究级难度"。**但在 v1 的真实 MDL 形态下，L6 可以退化成恒等变换，L5 可以退化成"表名替换"。**

原因：你的 54 个模型全部是

```yaml
name: EOrder
table_reference: { catalog: EVIAN_CDSP, schema: dbo, table: e_order }
columns: [{ name: orderId, type: INT, raw_type: int, ... }, ...]
```

即 **MDL 列名 == 物理列名**，没有 `expression`、没有 `ref_sql`、没有 view、没有 relationship。`wren-core` 在这种输入下的 `transform_sql` 输出，等价于：

```sql
SELECT <显式列清单> FROM "EVIAN_CDSP"."dbo"."e_order"
```

**所以我们不需要重写表达式、不需要 DataFusion、不需要 Calcite。** 只需要：

1. 把用户 SQL 里对模型名的引用，替换成一个 CTE 定义；
2. 用户 SQL 的其余部分（聚合、窗口、UNION、HAVING、子查询）**原样保留**。

这就是本方案能把 30～40 人周压到 12～16 人周的原因。代价是**能力边界必须冻结**，见 §3。

### 1.1 实测结论：关系不进引擎，计算列会（2026-11-10 补充，三次实验）

> 前提修正：客户明确"关系指表与表之间字段的关系，现在没维护，以后会维护"，并要求**不得因重写而让 Wren 的能力失效**。
> 因此不能靠"关系永远不会出现"来做设计，必须实测引擎到底用关系做什么。

用 `wren-core-py 0.8.0` + 真实 vendored 代码做了三个探针（临时 MDL 工程，不碰客户数据）：

| 实验 | 输入 | 实际输出 | 结论 |
|---|---|---|---|
| 关系路径引用 | `SELECT A.id, A.B.name FROM A`（manifest 已声明 A_B 关系） | `Schema error: No field named "A"."B".name. Valid fields are A.id, A.customerId, A.amount.` | **引擎不提供关系列，也不自动 join** |
| 显式双模型 JOIN | `SELECT A.id, B.name FROM A JOIN B ON A.customerId = B.id` | 两个模型各自展开为独立 CTE，JOIN 原样保留 | 关系只能靠"用户 SQL 显式写" |
| 复合关系（两列） | `ON A.customerId = B.id AND A.id = B.tenantId` | 同上，条件原样保留 | 复合键也只是提示词知识 |
| **计算列** | 列 `taxAmount: amount * 0.13`、`monthKey: DATE_TRUNC('month', created)` | MSSQL/PG：`DATE_TRUNC('MONTH', created)`；**MySQL：`STR_TO_DATE(CONCAT(YEAR(...),' ',MONTH(...),' 1'), '%Y %c %e')`** | **表达式由引擎内联进投影，且按目标方言翻译** |
| 视图 | `views/V/metadata.yml` 的 `statement` | 原样作为 CTE `V AS (...)` 注入，其引用的模型先生成 CTE | 视图是文本级注入，可低成本实现 |

**结论（关键）**：

1. **关系不丢**。Wren 把关系只当提示词知识与索引条目，引擎不消费它；Java 按同样方式处理即**功能等价**，不存在"阉割关系"。
2. **计算列才是真正的方言能力**。表达式是用 Wren/DataFusion 语法写的，靠 sqlglot 翻成目标方言（`DATE_TRUNC` → MySQL 的 `STR_TO_DATE`）。**纯 Java 透传会在 MySQL 上生成不存在的函数**。这才是"不阉割"要真正解决的问题。
3. **视图是文本级注入**，Java 约 100 行即可支持。

因此本方案把能力边界从"关系不支持"改成：**关系 ✅、视图 ✅、计算列 ✅（MSSQL/PG 原样透传；MySQL 需函数映射表）**，并新增一个可插拔的 `ExpressionTranslator`（§4.11）。

## 二、模块与依赖

```text
enterprise-mcp/
├── customer/semantic-api        # 纯接口 + DTO + 错误码，无第三方依赖
├── customer/semantic-core       # Java 实现（MDL/方言/执行/记忆/建模）
├── customer/app                 # 只依赖 semantic-api；按配置装配实现
└── customer/wren                # 保留为回归 oracle，不再进产物
```

依赖方向：

```text
customer/app -> customer/semantic-api <- customer/semantic-core
```

`semantic-core` 不依赖 `app`，也不依赖 `runtime` 的 Spring 组件；由 `app` 通过 `@Configuration` 装配。这样 `semantic-core` 可以用纯 JUnit + Testcontainers 独立测试，不被 MCP/权限/签名链路污染。

### 2.1 `semantic-api` 契约（这是解耦的实体）

```java
public interface SemanticEngine {
    SemanticHealth health();
    Optional<MdlSnapshot> current();                 // 全部数据源的聚合快照
    MdlSnapshot snapshot(String sourceKey);
    SemanticResult query(SemanticQuery query);       // 含 SQL 生成、校验、执行
    String dryPlan(String sourceKey, String mdlSql);
    void dryRun(String sourceKey, String mdlSql);
    List<DatasourceSummary> datasources();
    Map<String, String> datasourceDisplayNames();
}

public record MdlSnapshot(String aggregatedDigest,
                          Map<String, SourceSnapshot> sources) {}

public record SourceSnapshot(String sourceKey, String mdlDigest,
                             Map<String, Object> manifest, long version) {}

public record SemanticQuery(String sourceKey, String mdlSql, String question,
                            int limit, String expectedMdlDigest,
                            EmployeeLlm llm, boolean includeSql) {}

public record SemanticResult(List<String> columns, List<Map<String, Object>> rows,
                             int rowCount, boolean truncated, String sourceKey,
                             String mdlDigest, String retrievalStrategy,
                             Map<String, List<String>> columnLineage, String sql) {}
```

**关键约定：`semantic-api` 里的类型与 JSON 形状必须与今天 Adapter 的响应完全一致**，`WrenDatabaseTool` 只需要把 `Map<?,?>` 换成 `SemanticResult`，不改任何外部协议。这样切换实现对 Agent 透明。

## 三、v1 能力边界（必须先签字）

| 能力 | v1 | 处理方式 |
|---|---|---|
| `table_reference` 直映射模型 | ✅ 支持 | 生成 CTE |
| catalog/schema 三段限定符 | ✅ 支持 | 识别并归一化 |
| 显式列清单 / 隐藏列（`visible=false` / `isHidden`） | ✅ 支持 | 隐藏列不进 CTE 投影 |
| 中文 `display_name` / `description` | ✅ 支持 | 进 schema 描述文本 |
| 聚合 / 窗口 / UNION / CTE / 子查询 | ✅ 支持 | 用户 SQL 原样保留 |
| relationship（跨表 JOIN） | ✅ 支持 | 渲染进提示词 + 索引，LLM 写显式 JOIN；与现状完全一致（实测引擎本就不自动 join） |
| 关系列 `columns[].relationship`（引擎展开型） | ❌ 不支持 | **fail closed**：`UNSUPPORTED_MDL_FEATURE`（本 UI 不会产出） |
| 计算列 `expression` / `isCalculated` | ✅ 支持 | 表达式内联进 CTE 投影；经 `ExpressionTranslator` 处理方言 |
| view（`statement`） | ✅ 支持 | `statement` 原样作 CTE 注入，被引用模型先生成 CTE |
| cube / metric / hierarchy | ❌ 不支持 | fail closed |
| `ref_sql` 模型 | ❌ 不支持 | fail closed |
| 自定义函数 CSV（`function_path`） | ❌ 不支持 | fail closed |
| 数据源 | MSSQL / MySQL / PostgreSQL | 其他类型在建模期即拒绝 |
| 向量记忆 | ✅ 自研内存索引 | 不依赖 LanceDB |
| 建模控制台（内省/编辑/关系/候选提交/备份） | ✅ 支持 | 直连 Java 服务 |

**fail closed 的意义**：宁可明确报"该 MDL 使用了本版本不支持的建模特性"，也不能偷偷生成一条语义不同的 SQL 让客户拿到错数。

需要拦住的是 **`columns[].relationship` / `cube` / `metric` / `ref_sql` / `function_path`**。**普通关系、计算列、视图都是支持项，不在拦截范围。** 校验点放在两处：建模保存时（给出可读原因）、加载 MDL 时（升级后遇到老工程也不崩）。

> 现状提醒：本系统 UI 产出的 MDL 永远只有 table_reference 模型 + 关系，计算列与视图需要手工写 YAML 才会出现。因此这条守卫主要防"外部导入的 Wren 工程"。

> 真实能力收缩只有三处，必须在文档与销售口径里写清：**20+ 数据源、cube/metric、跨方言表达式的完整函数覆盖**。前两项本系统从未产出；第三项见 §4.11。

## 四、关键实现细节（真正的坑都在这里）

### 4.1 MDL → manifest：与 Python 逐字节对齐

Python 侧（`context.py`）做的事比想象中简单：**YAML 原样透传 + 递归 key 转 camelCase + 打 `layoutVersion`**。

```python
manifest = _convert_keys(build_manifest(project_path))   # 全部 key: snake→camel
manifest["layoutVersion"] = _LAYOUT_VERSION_MAP.get(sv, 1)  # {1:1,2:1,3:2,4:3,5:3}
```
`_normalize_model_columns` 只做两件事：`columns` 缺失则不加；非 list 置空；非 dict 元素丢弃。

Java 实现必须复刻的三个易错点：

1. **YAML 解析器语义**。PyYAML `safe_load` 是 YAML 1.1：`yes/no/on/off` → bool，`2026-01-01` → `date`，`1.0` → float，`010` → int 8。SnakeYAML 默认也是 YAML 1.1，但边界（如 `~`、空值、`!!binary`、锚点合并 `<<`）需逐项对齐。**做法：把客户两个真实 project 的每个 YAML 文件，用两边解析器各输出一份 canonical JSON，做字节 diff，作为门禁测试。**
2. **camelCase 转换的歧义**。Python 用 `_snake_to_camel`，但有一张 `_CAMEL_TO_SNAKE_MAP` 反向表覆盖特殊情况（`refSql`、`notNull`、`isPrimaryKey`、`dataSource`、`layoutVersion`…）。Java 侧必须把这张表逐条搬过来，否则 `not_null` → `notNull` 还是 `notnull` 会不一致。
3. **数字/日期落 JSON 的形态**。Python `json.dumps(default=str)` 把 `date` 变 `"2026-01-01"`、`Decimal` 变字符串。Java 侧必须在序列化前把 YAML 的 `Date`/`BigDecimal` 显式转成同形态字符串，不能依赖 Jackson 默认。

### 4.2 Canonical JSON（P3 的唯一正确做法）

```java
ObjectMapper M = JsonMapper.builder()
    .enable(SerializationFeature.ORDER_MAP_ENTRIES_BY_KEYS)
    .disable(JsonWriteFeature.ESCAPE_NON_ASCII)   // 对齐 ensure_ascii=False
    .build();
// 输入必须是 TreeMap（递归有序），separators 由 Jackson 默认无空格保证
String canonical = M.writeValueAsString(sortedTree);
String digest = sha256Hex(canonical.getBytes(UTF_8));
```

对齐清单（逐项验证，不做假设）：

| CPython `json.dumps` 行为 | Java 对应 | 验证方式 |
|---|---|---|
| `sort_keys=True`（含嵌套） | 递归 `TreeMap` + `ORDER_MAP_ENTRIES_BY_KEYS` | 嵌套样例 diff |
| `separators=(",",":")` | Jackson 默认无空格 | 逐字符比较 |
| `ensure_ascii=False` | 关闭 `ESCAPE_NON_ASCII` | 中文列名用例 |
| 浮点最短往返表示 | `Double.toString` / `BigDecimal` 保留原 scale | `1.0`、`0.1` 用例 |
| 控制字符转义 `\u0001` | Jackson 默认同样转义 | 构造用例 |
| `true/false/null` | 一致 | — |

**门禁**：`MdlDigestParityTest` —— 对 `projects/current/{shuiqu_db,yiyun_db}` 两套真实 MDL，Java 计算出的 `mdlDigest(source)` 与 `mdlDigest(aggregate)` 必须与 Python 输出**字符串相等**。不等则整个方案停止，不允许"差不多"。

聚合摘要同样要复刻：`sha256(json.dumps({source: digest} for source in sorted(sources)))`，空源返回 `""`。

### 4.3 SQL 策略与 CTE 注入

解析用 **JSQLParser 5.x**（Apache-2.0，`StatementFeatures` 可直接判读写）。

**只读校验**（对齐 `_validate_read_only_sql`）：

```java
Statement st = CCJSqlParserUtil.parse(sql);
if (statements.size() != 1) reject("exactly one read-only query is required");
StatementFeatures f = st.getFeatures();
if (f.mayModifyData()) reject("write or administrative SQL is forbidden");
if (containsAnyLimit(st)) reject("LIMIT is forbidden; the adapter enforces the result row limit");
if (hasBareStar(st))     reject("SELECT * is forbidden; output columns must be explicit");
```

注意两个与 sqlglot 的差异，要写进测试：
- `COUNT(*)` 里的 `*` 必须放行（sqlglot 侧是 `isinstance(star.parent, exp.Count)` 例外）；
- JSQLParser 的 `mayModifyData()` 覆盖 `RETURNING` 和数据修改 CTE，正是我们要的（JSQLParser 官方文档明确这三个陷阱）。

**CTE 注入**：

```java
// 1. 收集用户已定义的 CTE 名，避免误判
Set<String> userCtes = collectCteNames(st);

// 2. 逐 Table 引用解析
for (Table t : findAllTables(st)) {
    if (userCtes.contains(fold(t.getName()))) continue;
    ModelDef m = registry.resolve(sourceKey, t.getFullyQualifiedName(), fold);  // 大小写按方言
    if (m != null) {
        ctes.add(buildModelCte(m, quotingOf(t)));   // 关键：沿用用户书写的引号形态
        replaceWithName(st, t, m.name());
    } else if (isViewOrUnsupported(t)) {
        throw unsupported();
    }
    // 否则：物理表直通（见 §4.6 安全口径决策）
}

// 3. 前插到用户 WITH 之前，保留原有顺序
```

`buildModelCte` 产物（MSSQL 示例，实际引号按方言）：

```sql
"EOrder"("orderId","orderNo","eid","shopId",... ) AS (
  SELECT "orderId","orderNo","eid","shopId",...
  FROM "EVIAN_CDSP"."dbo"."e_order"
)
```

**三个必须做对的边角**（来自 `CTERewriter` 的血泪）：

1. **大小写与引号**：模型 CTE 暴露的列名必须与用户 SQL 里书写的引号形态一致，否则在 MySQL（列名大小写不敏感但结果列名保留）和 MSSQL（默认 CI）上绑定/取列会错位。
2. **三段限定符归一化**：用户写 `EVIAN_CDSP.dbo.e_order` 时要认出来它就是模型 `EOrder`，不能当物理表直通（上游 `_normalize_semantic_table_qualifiers` 就是在做这件事）。
3. **重复列名**：用户 `SELECT a.id, b.id` 时不包裹子查询（上游 `_apply_limit` 注释明确：`SELECT * FROM (...) LIMIT n` 会触发 `ER_DUP_FIELDNAME`）。

### 4.4 执行与类型映射（P4）

```java
// limit+1 取一行判截断，与 server.py query() 完全一致
try (PreparedStatement ps = conn.prepareStatement(applyLimit(sql, limit + 1));
     ResultSet rs = ps.executeQuery()) { ... }
```

`applyLimit` 按方言分支（对齐 connector）：

| 方言 | 做法 |
|---|---|
| MySQL / PG | `sql\nLIMIT n` |
| MSSQL | 无 ORDER BY 时 `SELECT TOP n`；有 ORDER BY / OFFSET 时 `OFFSET 0 ROWS FETCH NEXT n ROWS ONLY` |

**类型映射表**（必须显式，不能交给 Jackson 默认）：

| 源类型 | Python 现状 | Java 目标 | 陷阱 |
|---|---|---|---|
| `DECIMAL/NUMERIC` | `decimal.Decimal` → `json.dumps(default=str)` → `"12.34"` | `BigDecimal` → `WRITE_BIGDECIMAL_AS_PLAIN` **并按字符串输出** | 输出成数字会改变 Agent 侧解析与 Excel 精度 |
| `BIT/BOOLEAN` | `bool` | `Boolean` | — |
| `DATETIME/DATETIME2` | naive `datetime` → ISO | `Timestamp` → `LocalDateTime` → ISO，**固定 `Asia/Shanghai`** | 用 JVM 默认时区会整体偏移，日期可能差一天 |
| `DATE` | `date` → `"2026-01-01"` | `LocalDate` | 同上 |
| `VARCHAR/NVARCHAR` | `str` | `String` | 中文/emoji 编码 |
| `NULL` | `null` | `null`（不是空串） | — |
| 列名 | 数据库原样 | 数据库原样（`ResultSetMetaData.getColumnLabel`） | 不能 `.toLowerCase()` |

**门禁**：`ResultContractTest` —— 同一 SQL 在两个实现下产出 `columns/rows/truncated` 的 JSON 逐字段相等（含 DECIMAL、DATETIME、NULL、中文列名、重复列名、超限截断 6 组）。

### 4.5 向量记忆：直接丢掉 LanceDB

现状：`schema_memory` + `query_memory` 存在 LanceDB，按 `source/<mdlDigest>/<modelHash>/` 分目录，带 `metadata.json` 指纹（`fingerprint`/`embeddingModel`/`dimension`/`records`/`queryRecords`）。

规模实测：54 模型 × 平均约 30 列 ≈ **1600 条 schema 记录**；1536 维 float32 ≈ **9.8 MB**。

**1600 次余弦点积在 JVM 里是微秒级**。所以：

- 索引 = `float[][] vectors` + `String[] texts` + `String[] payload`，全量常驻内存；
- 落盘格式自定义（`vectors.bin` + `meta.json`），保留原有目录层级与指纹字段，**升级时自动重建而不是读旧 `.lance`**；
- `embeddingModel` 维度变化 → 同现状：报 `embedding model dimension changed; rebuild the memory index`；
- rerank 保持"失败降级为向量顺序"的语义（`retrieval.py:169` 的行为）。

净收益：少一个 128MB 级原生依赖、少一类崩溃源、索引可原子替换且可读。

### 4.6 一个必须现在决定的安全口径

现状：`engine.py` 的 `fallback=True` + `strict_mode` 默认未开 → **用户 SQL 里出现非 MDL 的物理表时，会被放行直通到数据库**。

单进程重写是收紧这个口子的最佳时机：**v1 默认 `strict=true`，只允许 MDL 模型/视图**，物理表直通报 `TABLE_NOT_IN_MDL`。

但这是行为变更，需要产品确认：如果现有客户已经在用"模型名 + 物理表混写"的 SQL，收紧会打断他们。默认建议：**先跟随现状（`strict=false`）保证零回归，同时在配置里提供 `enterprise.semantic.strict=true`，下个版本切默认**。

### 4.7 并发与生命周期

```java
final class MdlRegistry {
    private final ConcurrentHashMap<String, SourceState> states;   // SourceState 不可变
    private final AtomicReference<String> aggregatedDigest;

    SourceState pin(String sourceKey);      // 查询入口取快照
    void commit(String sourceKey, long expectedVersion, MdlCandidate candidate);  // CAS
}

record SourceState(long version, String digest, Manifest manifest,
                   EngineHandle handle, AtomicInteger refs) {}
```

- **查询**：pin 快照 → 执行 → `refs--`；
- **提交**：`compute()` 里比对 `expectedVersion`（不等则 `CURRENT_MDL_CHANGED`）→ 换新 `SourceState` → 旧 handle 进入 retire 队列，`refs==0` 时关闭连接池；
- **连接池**：每源 HikariCP，`maximumPoolSize=2~4`（现在 Python 是单连接串行，别一上来开 20 个把客户库打挂）；
- **摘要校验保留**：`expectedMdlDigest` 从"跨进程防读到新 MDL"变成"计划绑定校验"，是 control-plane 契约，**不能因为同进程就删**。

### 4.8 建模与内省迁移

`admin_service.py` 1426 行的职责要原样搬到 Java，且**不能"顺手简化"**：

| 语义 | 现状 | 迁移要求 |
|---|---|---|
| 两步提交 | `prepare_mdl` 出 `candidateToken` → control-plane 确认 → `commit_mdl(expectedMdlDigest)` | 必须保留，否则破坏 `CONTEXT.md` 定义的 MDL Update 原子性 |
| 乐观锁 | `revision` 参数，冲突 `409 MODELING_CHANGED` | 必须保留 |
| 冲突码 | `PROFILE_IN_USE` / `CURRENT_MDL_CHANGED` / `INTROSPECTION_IN_PROGRESS` → 409 | 必须保留 |
| 目录布局 | `projects/current/<src>/models/<Model>/metadata.yml` | 必须字节级不变 |
| 内省 SQL | `_metadata_queries()` 按方言分支 | 逐条搬（这是数据源元数据的唯一来源） |
| 备份 | zip + 校验；`restore` 兼容旧包 | 明确 v1 写入/读取，旧包向上迁移 |
| 审计 | `audit/wren-admin-audit.jsonl` | 格式不变，追加记录 |

### 4.10 关系的处理（客户已确认后续会补关系，v1 即需具备）

#### 4.10.1 关系在系统中的两层含义，别混

| 形态 | 存放位置 | 谁负责展开 | 本系统是否会产出 |
|---|---|---|---|
| **关系定义**（join 条件） | `relationships.yml` | **LLM**：读到提示词里的 `Condition`，自己写 `JOIN ... ON ...` | ✅ 会（建模 UI 保存时写入） |
| **关系列**（`columns[].relationship`） | 模型 `metadata.yml` 的 `columns` | **引擎**：`wren-core` 自动补 join | ❌ 不会（`_persist_modeling` 只写物理列） |

Java 实现只需处理第一种；第二种 fail closed。

#### 4.10.2 Java 必须复刻的提示词片段

`schema_indexer.describe_schema()` 的顺序是：`Catalog/Schema` → 全部 models → 全部 relationships → views → cubes。关系片段格式（注意缩进两个空格、`→` 是 U+2192、末尾留空行）：

```text
### Relationship: {name}
  {left} → {right} ({joinType})
  Condition: {condition}
```

**必须逐字符对齐**，理由不是洁癖：提示词文本变化会改变 LLM 输出分布，一旦准确率下降，你无法判断是"引擎换了"还是"提示词换了"。建议把 `describe_schema()` 的输出固化成 fixture（同一个 manifest 输入 → 期望文本），作为 S2 的门禁之一。

#### 4.10.3 `relationships.yml` 的读写契约

```yaml
relationships:
- name: EOrder_EClient
  models: [EOrder, EClient]
  join_type: MANY_TO_ONE          # ← 注意：这里塞的是基数，不是 join 类型
  condition: EOrder.clientId = EClient.id
  properties: {status: CONFIRMED, source: MANUAL}
```

**注意 `join_type: MANY_TO_ONE` 这个语义重载**：`_persist_modeling` 把 UI 的 `cardinality` 直接写进了 `join_type`；而 `_describe_relationship` 又把它当 join 类型渲染给 LLM。在当前系统里这是"能工作"的（LLM 恰好需要知道基数），但它是**语义重载**——真按 Wren 规范（`join_type` 应为 `LEFT/INNER/...`）传给上游引擎会是非法值。

重写时有两个选择，必须显式决策：

| 选择 | 优点 | 代价 |
|---|---|---|
| A. 照抄现状（`join_type` 存基数） | 提示词文本零变化，零回归 | 语义债继续存在，未来对接真 Wren 引擎会炸 |
| B. 拆成 `join_type` + `cardinality` 两个字段 | 语义正确，可扩展 | 提示词文本变化 → LLM 行为变化 → 需要重新验收 |

建议 **A 用于 v1（零回归优先），B 作为独立小版本的单点变更**，并配上准确率对比，不要和引擎重写混在一次上线里。

#### 4.10.4 关系加入后仍需警惕的点

- **关系确实会进向量索引，Java 必须一起迁**（早前判断有误，已核对更正）：`extract_schema_items()` 会为每条关系产出一条 `item_type=relationship` 的记录，文本形如 `Relationship 'X': A → B (MANY_TO_ONE). Condition: A.x = B.y.`，且 `model_name` 填左端模型。漏掉它会导致"模型多到切向量检索后，关系提示消失、JOIN 变少"——这是最容易被忽略、又最难归因的一类回归。
- **多跳关系**：LLM 要自己串 `A→B→C` 的 join。关系越多提示词越长，越容易漏 join 或重复 join。与引擎实现无关，但会被误判成"重写导致变差"。验收必须单列"关系问答准确率"基线。


### 4.11 计算列与视图：怎么做到"不阉割"

#### 4.11.1 计算列的真实行为（实测）

`columns[]` 里带 `is_calculated: true` 的列，`wren-core` 会把它 **内联进模型 CTE 的投影**：

```sql
-- MDL: taxAmount = amount * 0.13, monthKey = DATE_TRUNC('month', created)
-- MSSQL 输出
SELECT [A].[id] AS [id],
       DATE_TRUNC('MONTH', [A].created) AS [monthKey],
       [A].amount * 0.13 AS [taxAmount]
FROM (SELECT ... FROM [CAT].dbo.orders AS __source) AS [A]
```

注意 `MONTH` 被大写成常量、`DATE_TRUNC` 保持原样——这是 **sqlglot 的方言渲染**。同一表达式在 MySQL 下会被改写成：

```sql
STR_TO_DATE(CONCAT(YEAR(`A`.created), ' ', MONTH(`A`.created), ' 1'), '%Y %c %e') AS `monthKey`
```

**这就是"阉割"的真正所在**：如果不做方言翻译，MySQL 上会生成不存在的 `DATE_TRUNC`，查询直接报错。

#### 4.11.2 设计：`ExpressionTranslator` 可插拔

```java
public interface ExpressionTranslator {
    /** 把 MDL 中的表达式（Wren/DataFusion 语法）渲染为目标方言。 */
    String toDialect(String expression, SqlDialect dialect);
}
```

三个实现，按部署选择：

| 实现 | 覆盖 | 适用 | 风险 |
|---|---|---|---|
| `PassthroughTranslator` | 原样输出 | MSSQL / PostgreSQL（实测这两者与 Wren 语法基本一致） | MySQL 下含日期函数的表达式会失败 |
| `FunctionMapTranslator` | 内置约 30～50 条常用函数映射（`DATE_TRUNC`/`DATE_ADD`/`CONCAT`/`IFNULL`/`CAST`…），未命中则拒绝 | MySQL 为主，表达式可由你逐条审查 | 未命中要报错而不是猜（fail closed） |
| `PythonTranslator`（可选） | 经 JVM 内嵌 CPython 调 `sqlglot.transpile` | 表达式复杂、需要 30+ 方言 | 多一个原生边界（见 §4.11.4） |

**推荐落地顺序**：`PassthroughTranslator` → `FunctionMapTranslator`（把客户实际用到的函数逐条补）→ 只有当"表达式不可枚举且跨方言"成为真问题时才上 CPython。

这套设计的价值：**能力边界是"函数覆盖度"，可以随使用逐步逼近全量**，而不是一次性的"支持/不支持"。这比"v1 砍掉计算列"要诚实得多。

#### 4.11.3 视图：文本级注入

实测：`views/<name>/metadata.yml` 的 `statement` 被**原样**作为 CTE，其引用的模型先生成 CTE：

```sql
WITH A AS (...), B AS (...),
     V AS (SELECT A.id AS id, B.name AS cname FROM A JOIN B ON A.customerId = B.id)
SELECT V.id, V.cname FROM V
```

Java 实现步骤：

1. 解析 `statement`（JSQLParser，按源方言），收集其中的表引用；
2. 若引用的是模型 → 先生成模型 CTE；若引用了另一个视图 → 递归（需环检测）；
3. 把 `statement` **原样**插入为 `V AS (...)`，不做任何改写；
4. 视图体里的列别名与类型不做校验（与上游一致）。

成本约 100～150 行，无研究性难点。

#### 4.11.4 什么时候才需要内嵌 CPython

只有当以下条件**同时**成立，才值得引入 JVM 内嵌解释器（JEP/JPype，仍是单 OS 进程）：

- 客户在 MySQL/PG 上大量使用含**方言差异函数**的计算列；
- 函数清单无法枚举，`FunctionMapTranslator` 命中率长期低于 90%；
- 团队接受"原生崩溃会带走 JVM"这一风险。

此时收益是"保留 sqlglot 全部 31 方言 + lineage"，代价是打包多出 libpython + sqlglot（约 30～40MB，远小于现在 400MB 的 Python 运行时），并且多一个必须做崩溃兜底的边界。

**当前不建议直接上**：你的主库是 MSSQL，实测 MSSQL 下表达式与 Wren 语法一致，`PassthroughTranslator` 即可正确工作。

> 注意一个与引擎无关的坑：MSSQL 的 `DATE_TRUNC` 只有 SQL Server 2022+ 才有。若客户是 2016/2019，即使引擎不换也会运行时报错——这属于表达式写法问题，应在建模 UI 给出提示，而不是丢给引擎。

## 八、明确不做

1. 不实现 `wren-core` 的 **cube / metric / hierarchy / `ref_sql` / 关系列（`columns[].relationship`）的引擎侧 join 展开**——一律 fail closed。这几类本系统 UI 从不产出，只在外部导入的 Wren 工程里出现。

4. 不改 MDL 文件格式、目录布局、`profiles.yml` 结构；`join_type` 重载在 v1 保持原样。

6. 不在 v1 承诺 20+ 数据源（真实收缩项，必须写进口径）。

8. 不用"近似翻译"兜底未知表达式：未命中函数映射就报错并给出表达式原文，由人决定怎么补。
